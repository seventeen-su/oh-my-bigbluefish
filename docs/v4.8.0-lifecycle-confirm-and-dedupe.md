# OMB v4.8.0 — 候选确认与跨路径写入去重

> 承接 v4.7.0 的事件驱动记忆控制器：控制器把非显式长期偏好写成 `assertedBy=model`
> 的**候选**，但候选此前没有任何确认入口；同时同一条内容经"控制器自动写 / 重复捕获 /
> 模型 `omb_remember`"三条路会变成多条记录。本版补上这两个缺口。
> 按 `x1.x2.x3` 纪律：新增用户入口与写入规则 → **4.8.0**。

## 1. 候选为什么需要确认入口

`modules/memory/lifecycle.ts` 的规则是"写入时是什么证据，就停在对应的阶段；
想升级只能由用户显式确认"。控制器据此把自动捕获的长期偏好停在**候选**——这是对的
（不冒充已确认），但**手动晋升一直是空的**：候选只能靠"再显式说一遍"覆盖，
库里因此长期堆着永远不会升级的条目。缺的不是自动晋升（那会违反不变量），是用户入口。

### 1.1 `/omb-confirm`

```text
/omb-confirm                 列出当前可见库里的候选（最近 50 条/库里筛，最多显示 5 条）
/omb-confirm <记忆id>         把该候选确认为"已确认"
```

- **只注册斜杠命令，不新增模型工具**：确认改变的是证据等级，只有用户有权把
  "系统推断"升格为"用户确认"（与 `/omb-privacy`、`/omb-feedback` 同一原则）。
- 命令不可用不影响记忆写入/召回；`confirmCommand: false` 可关闭。

### 1.2 确认的语义：只改证据归属

| 字段 | 确认后 |
| --- | --- |
| `assertedBy` | `model` → `user` |
| `id` / `text` / `contentHash` / `sourceRef` / `observedAt` | **一字不改** |
| `validTo` / `supersededBy` / `lastUsedAt` / `useCount` | 保留（确认不是"重新观察"） |
| 生命周期阶段 | 候选 → 已确认（`procedural` 时 → 经验） |

只接受真正的候选：`semantic`/`procedural` + `assertedBy:model` + 未失效 + 未被取代。
事件条目、已失效、已被取代、已是 `user`、`execution` 的一律拒绝并说明。
写回后**查回验证**（id + contentHash + `assertedBy=user`），验证失败不谎报成功。
确认是单向的（当前没有"退回候选"的命令），文档不假装可撤销。

### 1.3 隐私

与 `/omb-feedback` 同一闸门：sealed 不读；read-only 与归属未知不写。
确认不会因为"只是改归属"而绕过隐私。

## 2. 跨路径同内容去重

### 2.1 问题

库按 `id` upsert，但**没有正文唯一索引**。同一条内容会从三条路进来：

1. 控制器 `persist` 自动写入；
2. 重复捕获（同一消息重放/多会话撞同一句）；
3. 模型主动 `omb_remember`。

捕获路径本来就用「正文前 60 字符词法探测 + `contentHash` 精确比对」去重，
但 `omb_remember` 没有。于是"库里已有同内容"时模型一写就多一条：
召回时彼此挤占名额，冲突判断会把"同一条"当成"两条不同结论"。

### 2.2 做法

把判据抽成 `remember.ts` 的 `findSameContent(store, text)`：

- 捕获路径（`capture.ts` 的 `alreadyStored`）与 `omb_remember` **共用同一份**；
- 只认**活跃**条目（`searchLexical` 已过滤 `valid_to`/`superseded_by`）——
  旧结论被取代后再次写同一句仍会正常落库（那是新事实，不是重复）；
- 命中时**不写、不触发 `memory/written`、不触发向量编码**；
- 回执给出已存在条目的 `id`、`scope/kind`、**阶段**与原文摘录；
  若它是候选，附上 `/omb-confirm <id>` 用法；
- 查询失败一律返回 `undefined`（去重是优化，不是安全边界，不能阻断写入）。

去重放在**准入之后**：准入是"该不该记"，去重是"是否已经记过"；
先准入再查重保证弃权计数与既有权重逻辑完全不变。

### 2.3 没有做什么

- 不加正文唯一索引（需要 schema 迁移，且"同句不同来源"有时是合法事实）；
- 不做近义改写去重（那是离线整合的职责，在线路径保持确定性）；
- 不阻止"同一内容写进用户库与项目库各一份"（作用域不同，问题不同）。

## 3. 状态面

- `/omb-confirm` 读数：`confirm.commands / listed / promoted / refused`；
- 记忆健康行只在**按过命令后**追加：
  `；候选确认：已确认 N 条（命令 M 次，列出 K 次[，拒绝 R 次]）`
- 没按过命令、未接线：一个字都不写（不把"没发生"印成"确认了 0 条"）；
- 文案由导出的 `confirmHealthNote()` 生成，单测直接钉住。

## 4. 明确未做（其中两项已在 v4.8.1 收尾）

1. **没有自动晋升**：候选只能由用户确认（不变量不变）。
2. ~~**确认不可撤销**~~：v4.8.1 提供 `/omb-confirm undo <id>...`（带审计、可批量）。
3. ~~**列表只有一页**~~：v4.8.1 支持 `/omb-confirm list [offset]` 与"还有 N 条未显示"。
4. **去重只认精确同内容**：不做向量近似、不做跨作用域去重。
