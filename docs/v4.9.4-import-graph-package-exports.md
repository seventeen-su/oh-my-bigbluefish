# OMB v4.9.4 — 项目画像：workspace 包导出映射

> 既有"导入图"的细化（x3）：原来的文件级导入边只认相对路径与 tsconfig 别名，
> 裸包名（`@demo/core`）会被当成"第三方依赖"跳过——即使它就在 `packages/` 里。
> 本版按 workspace `package.json` 的 `main`/`types`/`exports` 把包名映射到仓库内入口文件。

## 1. 做法

- `readPackageEntryMap(root)`：扫描 `packages/*/package.json`（最多 32 个包），
  收集 `name` 与入口候选（`main` / `types` / `typings` / `exports` 的 `.` 分支），
  再补 `index.ts` / `index.js` / `src/index.ts` / `src/index.js` 兜底；
- `resolveImportTarget` 的解析顺序：
  ① 相对路径 → ② tsconfig `paths` 别名与 `baseUrl` → ③ **workspace 包名**；
- 包名支持子路径（`@demo/core/src/foo`），仍只认**仓库内真实存在**的文件，
  越界（`..`）、不存在、非文件一律跳过；
- 解析结果与相对导入一致：写进 `structure.fileImports`，目录级聚合进
  `structure.imports`；近似调用边（`calls`）同样适用（跨包符号也能连）。

## 2. 为什么不做"完整类型图"

"包导出映射"与"类型解析"是两件事：

| 能力 | 本版 | 完整类型图 |
| --- | --- | --- |
| 裸包名 → 入口文件 | ✅ 静态读 `package.json` | 需要 TS program |
| 类型/签名/泛型解析 | ❌ | 需要 TypeScript 编译器 API |
| 代价 | 一次目录扫描（有界） | 加载编译器 + 按项目规模秒级代价 |

画像的读取路径有预算（≤2400 字符、扫描上限、缓存刷新），把编译器塞进来会让
`omb_project` 从"廉价快照"变成"重任务"。当前导入图回答的是"模块怎么依赖"，
完整类型图属于"类型检查"职责（由 `tsc` 承担）。边界见
[`v4-remaining-closure.md`](v4-remaining-closure.md)。
