# 上下文预算：常驻提示该放什么、放不下什么

本文回答一个具体问题：**"让模型知道该去查记忆库"这件事，放哪里最省？**

起因是 `omb_status` 的拉取台账显示 `omb_recall` 长期趋近 **0 次/轮**：模型不是不会用，
是**想不到用**。而定位到两处缺口：

1. **机制层**：向量通道当时降级为哈希词袋（字符重合，非语义）；
2. **触发层**：模型的常驻上下文里**没有任何一句话**提到记忆库。

本文只处理第 2 条。第 1 条的修法是装模型，见文末。

---

## 一、先量清楚预算：常驻提示总共只有 120 字符

| 事实 | 值 | 出处 |
| --- | --- | --- |
| 常驻提示总预算 | **120 字符** | `kernel/abi/host.ts:93` `RESIDENT_HINT_MAX = 120` |
| 推理模块已占用 | **104 字符** | `omb_status`「常驻提示 104/120 字符」 |
| 剩余 | **16 字符** | —— |

而且常驻提示是**所有模块 `resident` 字段拼接后统一截断**的
（`dsh/session.ts:90-96`：`parts.join('\n')` 后 `slice(0, RESIDENT_HINT_MAX)`）。

**这意味着：新增一条记忆常驻提示，不是"多花几十个 token"，而是要么截掉推理那条的尾巴，
要么抬高全体模块的成本上限。**

## 二、还有一条硬约束：必须逐字节稳定

`dsh/session.ts:86-88` 写着：

> **逐字节稳定是硬要求**：常驻提示进入系统提示的稳定前缀，任何跨轮变化都会使其后的
> 整段前缀缓存失效。

这条约束**排除了一整类"聪明"方案**：

| 被排除的方案 | 为什么更贵 |
| --- | --- |
| 只在"问题看起来像要回忆"时才注入 | 提示时有时无 → 系统提示前缀每轮都变 → **每轮全量缓存未命中**。省下的几十 token 远不够赔 |
| 带上"本会话已召回 N 条"之类的计数 | 同上，且计数每轮都变 |
| 按压力档位决定要不要提醒 | 同上；压力档位本身就是变化的 |

顺带说明：`dsh-desktop-notify` 生态里那个 `system-anchor.ts` 就是为对抗这类前缀抖动写的
（把首次见到的 head 文本粘住、逐字节转发）。**我们不该自己制造它要修的问题。**

## 三、三个候选位置，只有一个是划算的

| 位置 | 边际成本 | 是否与能力同处 | 结论 |
| --- | --- | --- | --- |
| **新增 `prompt:omb-memory` 常驻段** | 与推理段**争抢同一个 120 预算**，或抬高上限让全体变贵 | 否（模型要在系统提示与工具清单之间对照） | ❌ |
| **写进易变上下文槽**（`context()`） | 每轮重算 → 前缀缓存必然失效 | 否 | ❌ |
| **写进 `omb_recall` 的工具描述** | 描述本来**每轮都在**上下文里，只是多几十字符；不占常驻预算 | **是**——模型正是在"考虑用哪些工具"时读它 | ✅ |

第三条同时符合 `agent-experience` 技能的两条规则：

- *"Put parameter rules on the parameter"*——"什么时候用"属于这个工具的说明，就该在它身上；
- *"Say each fact once"*——已经有一条常驻提示了，同样的意思在第二处再说一遍是重复。

## 四、落地

`modules/memory/recall.ts` 的 `omb_recall` 描述**开头**加了一句触发条件：

> 当问题涉及"之前 / 上次 / 我们说过的 / 我的偏好 / 以前定过的方案"，或者当前任务看起来是
> 过去某次工作的延续时，先查这里再回答——跨会话的既往结论只存在于此，不在你的上下文里。

放开头而不是结尾，因为它是这个工具原先**唯一缺**的那一句：原描述只说了"能召回什么"，
没说"什么时候该来召回"。

**成本**：**实测 93 字符**（初次写的是"约 70"，是估的——改成实测值，并把方法记在这里：
从 `modules/memory/recall.ts` 里取出该段字符串字面量拼接后的长度）。
它只加在工具描述里，**不动 120 字符的常驻预算**（推理那条仍是 104，不会被截断）。

**尚未做的一件事**：`agent-experience` 要求"改了工具定义就对比首轮 prompt token 数"，
而我**没有测**这 93 字符换算成 token 后的实际增量。上面算的是**字符**成本，不是 token 成本。
要补的话：同一会话在改动前后各取一次首轮 `contextPressure` 的 `pressureTokens`。

**为什么不做成常驻提示**：见上表——它不是"更贵一点"，而是要么挤掉推理、要么让全体变贵，
而且违反"同一件事只说一遍"。

## 附：第 1 条缺口（机制层）的修法

向量通道降级的根因是**权重目录不存在**，不是代码问题。修法是装模型：

```bash
pnpm fetch-embedding-model            # 量化版，约 24MB（默认）
pnpm fetch-embedding-model --variant fp32   # 未量化，约 95MB
OMB_MODEL_MIRROR=https://hf-mirror.com pnpm fetch-embedding-model   # 大陆网络
```

落点 `<仓库根>/models/bge-small-zh-v1.5/`，三个文件缺一不可：

| 文件 | 大小 | 来源 | 为什么不能少 |
| --- | --- | --- | --- |
| `model_quantized.onnx` | 164KB | `onnx-community/bge-small-zh-v1.5-ONNX` | 计算图 |
| `model_quantized.onnx_data` | 22.7MB | 同上 | 外部权重；**文件名写进了 ONNX 图内部，改名会导致会话创建失败** |
| `vocab.txt` | 107KB | `BAAI/bge-small-zh-v1.5` | 自实现 WordPiece 分词器只依赖它；缺 `[CLS]`/`[SEP]` 即拒绝装载 |

**为什么沿用 bge-small-zh-v1.5 而不是换更新的模型**：

- `modules/memory/onnx.ts` 是为它写的（`BGE_EMBEDDER_ID = 'bge-small-zh-v1.5-512'`、
  `BGE_DIMENSIONS = 512`、CLS 池化、WordPiece），换模型要同时改维度、分词器与既有向量；
- 量化后 23.8MB，是"本地进程内推理"量级里最合适的一档；
- 更强的选择（如 Qwen3-Embedding-0.6B）参数量高一个数量级、维度 1024，
  对桌面插件的常驻内存与首次装载时间都不划算——那是**有意的升级决策**，不是等价替换。

模型是**部署产物**，不进 git；`scripts/fetch-embedding-model.mjs` 保证可复现，
每个文件都按上游 LFS 的 sha256（词表按内置常量）校验，不一致就删除重下、绝不留下半份。
