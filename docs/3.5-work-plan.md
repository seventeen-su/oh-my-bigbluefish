## 1. 目标与验收（Definition of Done）

用户要求三件事：① 补齐已有组件的欠缺；② 挖掘并修复可靠性问题；③ 改进工程实现与局部效率。
落地成**可核对**的验收：

1. `pnpm verify` 全绿，且 **passed 数只增不减**（基线 1271），新增用例数能被逐条解释。
2. 每条修复都有**先红后绿**的判据：新测试在修复前必须失败（提交里写明"修复前失败"这一点是怎么验的）。
3. `node scripts/build.mjs` 换代到 **g80**，`node scripts/check-resolution.mjs` 通过（8 行可解析、可加载、有中文名）。
4. 真机（重启宿主后）：`omb_status` 代数 == `build-generation.json` 的 generation == 80；8 模块 0 降级 0 失败；
   §3 里列出的每条"读数说谎"类缺陷在状态面上**看不出矛盾**。
5. 版本号进位到 **3.5.0**（有内容变化 = minor；不是 patch，因为含行为变更：心跳默认关闭）。
6. 所有分支合并回 `main`，冲突已处理，`git log --oneline` 上每段工作一条可读的简练提交。

**明确不做**（沿用既有刻意取舍，不要在本次"完善"里翻案）：

- 模块开关前置条件的**运行时硬阻断**——`kernel/abi/catalog.ts` 头部与 `docs/v3-ten-item-plan.md` §五 已写明理由（会把"依赖晚一点就绪"误判成"依赖缺失"→ 静默丢能力）。

### 2.3 两条本轮实测出来的纪律（必须写进 `docs/parallel-work.md`，归 S5）

1. **绝不用 junction 给 worktree 共享 `node_modules`。**
   实测事故：探针 worktree 里的 `node_modules` 是指向主仓库的 junction，执行
   `git worktree remove --force <探针>` **穿过 junction 把主仓库 `node_modules` 清空**
   （`files=0`；`.omb` 记忆库 4 文件、`models` 权重 3 文件、`lib-gen` 86 文件、全部源码与 `git status` 均完好，
   损失只限依赖目录，`pnpm install --prefer-offline` **2.1s** 复原）。
   规则：每个 worktree 各自 `pnpm install`（store 热时实测 992ms–2.1s，代价可忽略）；
   若已存在 junction，删 worktree 前必须先 `cmd /c rmdir <junction>`（只删链接），**不要用 `Remove-Item -Recurse`**。
2. **子代理 fan-out ≤ 4，且每个代理必须把结果 `write` 落盘。**
   实测：7 并发审计整批失败，7 个子代理会话的 `turn/end` 全是
   `429 {"type":"GoUsageLimitError","message":"Go usage limit exceeded"}`，而 workflow 作业通知仍报 `status: completed, 7 agents`
   ——**作业"完成"不等于代理有产出**。同轮还实测到：长空闲（2h16m）后 `job_output` 报 `unknown job`、`job_list` 为空，
   **已完成作业的结果永久取不回**。所以落盘是主副本，作业返回值只是副本。

**a) 心跳：显式开启 + 硬上界（F1 + F6）**

- 契约（环境变量 `OMB_HEARTBEAT`，三态）：
  | 值 | 行为 |
  | --- | --- |
  | 未设置 / `0` / `off` / `false` / `no` | **不写**——`heartbeat()` 是零 IO 的空操作（默认） |
  | `1` / `on` / `true` / `yes` | 写 `<本包根>/.omb-heartbeat.jsonl` |
  | 其它非空值 | 当成路径写（相对路径按本包根解析；**保留原样大小写**，不参与真假值判定） |
- 每进程只解析一次：内建模块引用、包根推导、开关与落点全部缓存；解析失败也缓存（不重试）。
- 上界：单文件 > **4MB** 触发轮转（`X` → `X.1`，只保留一份）→ 磁盘占用硬上界 8MB；
  初值 `written` 取自 `statSync` 的现有大小（**跨进程也算数**，否则上个进程留下的 19MB 会被当成 0 继续追加）。
- **轮转失败就停写**（把状态清掉、不再重试）：理由是"上限守不住还继续无上限追加"正是要修的缺陷本身，不能一边修一边留后门。
- 落点仍由自身位置推导（保留原有理由：写死绝对路径会让独立副本反向写开发仓库）。
- 为可测性导出 `resetHeartbeat()`（让下次调用重读环境）与 `heartbeatSink()`（当前落点与已写字节）。
  **消费者是测试**——符合 `kernel/abi/catalog.ts:57-60` 那条"不要加没有消费者的字段"。
- 判据（会失败的测试）：① 未设环境变量时连续调用 100 次，`appendFileSync` 调用数为 **0**；
  ② `OMB_HEARTBEAT=<临时路径>` 且文件已被垫到超过上限时，一次调用后出现 `.1` 且新文件小于上限；
  ③ 解析一次后不再有 `existsSync`（缓存生效）；④ 落点不可写时 `heartbeat()` **不抛**（H-1）。
- 行为变更需写进 README（归 S5 落笔，S1 提供文案）：默认不再产生 `.omb-heartbeat.jsonl`。

**b) 宿主事件订阅失败不再静默（F2）**

- 现状：`kernel/adopt.ts:158-170`，`hostOn(event, fn)` 返回非函数或抛错时，直接落到内核总线，
  而 `HOST_ONLY_EVENTS`（`:96-103`：`session/event`、`session/flush`、`tools/result`、`tools/call`、`tools/execute`、`tools/post-execute`）
  的事件**只发在宿主事件面**（`dsh/hooks.ts`、`dsh/session.ts` 用 `ctx.on`）→ 订阅成功、事件永不到来、健康面全绿。

  **包装 `selfReport`**，使该模块之后任何一次健康上报都带上粘性后缀并把 `ok` 降为 `degraded`：
  `；⚠ 宿主事件面订阅失败 N 处（session/event…）——已回落内核总线，这些事件收不到宿主载荷`。

  ③ **反向断言**：宿主 `on` 正常返回函数时不得出现任何降级（不许把真告警一起打开成噪音）。
