## §0 结论摘要（10 条）

1. **记忆库不是"没数据"，是"数据分在两个物理面 + 质量差"**：用户库 16 行（avg 484 字符）、14 个项目库合计 55 行；`semantic` 只写用户库前 16 行里有 12 行是 `asserted_by=model`，内容是**模型自己的会话回顾/自检记录**，不是可复用的项目知识 [实测]。
2. **143 次写入 → 83 次准入（58%）**：47 次「没有准入依据」、5 次「缺少来源引用」、5 次「项目库尚未就绪」、2 次被第三方 `dsh-path-guard` 拒、1 次隐私 read-only 拒 [实测]。准入不是"过严"这么简单——它是**两条错误方向同时存在**：该拒的（模型回顾）被放进来 12 条，该放的（有来源的结论）被"没有准入依据"拒了 47 次。
3. **`userAsserted` 的核对链路是死代码**：`lastUserMessage` 依赖从未在生产装配里注入（`remember.ts:557,938` vs `modules/memory/index.ts:636-708`），所以 10 次「自称用户原话」全部记为 `claimed-unverified` [实测]。
4. **`execution:` 前缀是自签合格证**：准入第三条依据只看 `sourceRef` 字符串前缀（`remember.ts:239,322-333`），模型写 `sourceRef: "execution:本会话…"` 即可通过；项目库 3/3 行正是这种回顾体 [实测]。这与"工件的存在性核验"（`remember.ts:345-400`、`artifacts.ts:144`）形成鲜明反差：**能核验的那条真的核验了，不能核验的那条只核了字符串**。
5. **检索侧精度塌陷**：中文 FTS5 用 bigram + **OR** 连接（`text.ts:38-90`），词法通道**没有分数下限**（下限只给了向量通道，`vector.ts:643`、`onnx.ts:59`）。43 次有命中的召回里，**首条命中 32/43 集中在 9 条记录上**（「今天感觉还不错」「DSH 技能装上了但用不上」「SSH 公网约束」等），与本查询主题无关者过半 [实测，53 条真实召回逐条比对]。
6. **召回输出很贵**：默认 `limit=5` 且**返回全文**（`recall.ts:390-418`），按当前库真实行模拟一次召回 **3,877 字符 ≈ 2.4–3.2K token**；`limit` 上限 20 时可到 ~1.5 万字符 [实测 + 字符/token 换算属 [推测]]。
7. **触发依赖一句工具描述**：记忆模块**没有常驻提示、没有易变上下文注入**（`kernel/abi/host.ts:73-99` 提供该面，`modules/memory/index.ts:438-463` 未实现），模型只能从 222 字符的 `omb_recall` 描述知道"何时该查" [实测]。真实使用率：391 会话里 29 个写过（7.4%）、27 个查过（6.9%）。
8. **两个"零"是进程内读数，不是系统事实**：`omb_status` 的「已打开项目库 0 个」在首个回合前必然为 0（开库由 `turn/start` 预热，`index.ts:527-532`）；向量段「最近一次检索：尚未发生」是本进程计数（`vector.ts:785-791`）。历史证据反向：43 次召回命中 156 条、`use_count` 合计 40 [实测]。
9. **DSH 0.2.1-rc.2 原生会话检索已在本 profile 启用，但它救不了中文**：5 个只读工具 + 315 字符固定提示；索引是 `fts5(unicode61)` 字面短语检索（`session-query-sqlite/src/schema.ts:127-137`、README §Search behavior）[实测 + 报告]。我用 `node:sqlite` 最小实验证明：`unicode61` 下查询「记忆」**匹配不到**「长期记忆系统的写入准入过严」[实测]。真实使用量：391 会话里 `session_search` 只有 **6 次**（对比 `omb_recall` 52 次）[实测]。
10. **结论**：OMB 记忆的问题**不在数据结构（schema/迁移/向量归属做得比多数开源实现严谨），而在"写什么 + 怎么触发 + 怎么排序 + 报多少"**。重构优先级应为「触发与准入 > 检索精度与输出成本 > 生命周期与遗忘 > 表示法（图/层级）」。任何加 LLM 到热路径、加第二个常驻提示、或把会话历史搬进 OMB 的方案，本轮证据都反对。

## §1 OMB 记忆现在到底在做什么（架构追踪）

### 1.1 数据面：双库、单表、FTS5、版本化迁移

| 事实 | 证据 |
| --- | --- |
| 两个物理库：`$DSH_HOME/.omb/memory/knowledge.db`（跨项目）、`<cwd>/.omb/memory/session.db`（跨会话） | `modules/memory/paths.ts:4-13,19-21,74-80` |
| 表：`memory`（16 列，STRICT）、`edge`（3 类边、无权重）、`embedding`（主键含 model/dim/revision）、`meta`（单行）、`memory_fts`（FTS5 + 三个触发器同步） | `migrate.ts:207-299` |
| 迁移：`PRAGMA user_version` 驱动，v1→v2 纯加法（`embedding.content_hash`），旧库原地升级 | `migrate.ts:1-24,112-136,191-194,333-338` |
| 打开参数：WAL、`busy_timeout=1000`、`synchronous=NORMAL`、`secure_delete=ON` | `store.ts:1606-1650` |
| kind→库路由固定：`semantic→user`，`episodic/procedural→project` | `kernel/abi/catalog.ts:431`、`remember.ts:932` |
| 单条正文上限 4000 字符、最小 4 字符 | `remember.ts:41-44` |

**特点（应保留）**：`edge` 刻意无 weight（"未归一化的边权与融合是同一类量纲不可比错误"，`store.ts:1-30` 注释）；向量归属三要素（model_id/dim/revision）+ `content_hash` 让"换模型/改正文"可结构化判定（`migrate.ts:302-332`）。这部分是**超出同类开源实践**的工程细节，重构不应破坏。

### 1.2 写入路径：只有一个入口，且是"模型自觉"

```
omb_remember (remember.ts:904-1038)
  → decideAdmission (remember.ts:278-417)
      ① claimedUserAssertion + 用户消息核对
      ② 正文里出现工件标记 → verifyArtifact（git ls-files 核验，artifacts.ts:144）
      ②b sourceRef 显式且指向真实文件 → 核验
      ③ sourceRef 前缀 ∈ {execution:,command:,test:,run:,observed:}
  → store.put (store.ts:307-312：ON CONFLICT(id)，id = 时间+序号+哈希前缀，remember.ts:595-598)
  → emit memory/written → 向量编码队列
```

- **没有自动捕获**：模块不订阅 `user/message`，也不在回合结束时写摘要；记忆 100% 靠模型主动调用。
- **没有在线去重**：`content_hash` 只有普通索引（`migrate.ts:228`），不是唯一约束；同一段话在不同时刻写入会得到不同 id（`remember.ts:595-598`），重复只能等离线整合合并。
- **准入口径的意图是"精度优先"**（`remember.ts:411-416`：宁可漏记也不写入模糊印象），方向正确。

### 1.3 检索路径：只被工具触发，门控先行

```
omb_recall (recall.ts:307-352)
  → resolveStores（会话归属确定才给项目库；否则只用户库，recall.ts:480-494）
  → gateRetrieval (retrieve.ts:256-284)
      - mode=never / 无库 / kinds=[] / 空查询 / pressureBand=tight → 跳过
  → retrieve (retrieve.ts:521-697)
      - 每库：FTS5 BM25 通道 + 向量通道（若模块装载）
      - RRF 融合 k=60 (retrieve.ts:38)；候选上限 20/库 (retrieve.ts:42,547)
      - 水合 → 排除 omb-doc: 保留源 + valid_to 行 → 过时探测（searchOverturned）
      - 可选廉价重排：fusion .55 / recency .25 / usage .12 / asserted .08 (retrieve.ts:46)
      - 每库配额两遍填充 (retrieve.ts:432-458)
  → 记账 markUsed（只有成功注入才写，recall.ts:260-304）
  → renderRecall 全文渲染 (recall.ts:390-418)
```

- 门控是**一等结果**（返回空 + 原因），这个设计正确。
- 但 `pressureBand='tight'` 时**默认跳过检索**（`retrieve.ts:272-282`），且 `omb_recall` 的 JSON schema 里**没有 `mode` 参数**（`recall.ts:40-55`），模型无法用 `mode: always` 翻越。实测发生 2 次：回执为「门控跳过检索（pressure-tight）…（**没有可注入的记忆**：请基于当前上下文作答，不要编造记忆内容。）」——**"因预算跳过"被渲染成"没有记忆"** [实测，会话日志原文]。
- 词法通道 SQL：`memory_fts MATCH ? AND scope=? AND valid_to IS NULL AND superseded_by IS NULL ORDER BY -bm25(...) LIMIT ?`（`store.ts:1116-1127`）——**没有最低分过滤，也没有长度/类型降权**。

### 1.4 向量子通道：异步、可回填、512 token 截断、512 维

- 嵌入器：`bge-small-zh-v1.5-512`（512 维、revision 1、CLS 池化、自实现 WordPiece、`maxLength=512`），量化 ONNX ~23MB（`onnx.ts:30-59,129-169,459-538`；`docs/context-budget.md:93-110`）。
- 写入后不阻塞：`memory/written` 入队，`step/end` 时 `flushVectorEncoder(kernel, 32)`（`dsh/session.ts:810-824`）；队列上限 256、回填上限 32（`vector.ts:81-125`）。
- 查询余弦下限按嵌入器标定：BGE 0.375、哈希词袋 0（`vector.ts:544-546`、`onnx.ts:59`）。
- **一个未处理的长文本缺陷**：分词在 512 token 处直接 break（`onnx.ts:222-230`），而单条记忆可到 4000 字符（`remember.ts:41`）；当前库里 avg 484、max 1098 字符，多数条目接近或超过 512 token → **尾部内容不进向量**，只能靠词法命中 [实测代码 + 库内长度；影响程度 [推测]]。
- 库内实测：用户库 19 条 embedding = 16 条 BGE + **3 条残留 `hash-bow-256`**（旧模型行保留是"换回原嵌入器"的退路，有注释说明；不在当前归属下参与检索）。

### 1.5 离线整合与图

- 触发：`turn/end`（宿主 `step/end` 映射）+ 每 `consolidationEveryTurns=32` 个回合边界一次（`index.ts:62-66,554-582`；`dsh/session.ts:810-815`）。单次扫描最近 500 条（`index.ts:197`）。
- 纯函数计划器：近重复（shingles+Jaccard 阈值 0.7、blocking key 3）、矛盾（否定极性相反 + core token 重叠 ≥2 + Jaccard ≥0.6）、衰减先验（半衰期 30 天，只参与排序不落盘）、非破坏性 supersede（只写 `validTo/supersededBy`，不删行）（`consolidate.ts:26-41,246-337,342-641`）。
- 图：`edge` 三类 + 无向 BFS（depth≤2、节点≤20、边≤60）（`graph.ts:33-37,113-184`）。
- **机制齐但数据近乎为零**：用户库 `edge` 仅 1 条 `supersedes`；项目库 0 条。离线整合在生产中运行次数无法从 DB 直接读，只能从健康面（`index.ts:392-404`）看 `runs/lastMergedGroups` [实测 DB；运行次数未测量]。

### 1.6 隐私：是"会话门禁"，不是"数据最小化"

- 三档模式 `normal < read-only < sealed`，fail-closed 粘性标记，命令 `/omb-privacy` 设置，子代理继承（`privacy/modes.ts:4-30,117-125`；`privacy/codec.ts:1-24`；`privacy/durable.ts:8`）。
- 强制点在库访问边界惰性解析 `SERVICES.privacy`（`index.ts:500-505`、`store.ts:1838-1888`）。
- **没有** PII 检测/脱敏、没有字段级加密、没有写入时的密钥模式拒绝（全模块 grep `redact|PII|脱敏|敏感` 零命中）。记忆正文以明文存 SQLite；`omb_forget` 会截断 WAL 以清磁盘残留（`recall.ts:436-452`、`store.ts:830-832`）[实测]。

### 1.7 模型可见面（token 经济）

| 面 | 内容 | 成本 |
| --- | --- | --- |
| 常驻提示 | 记忆模块**零贡献**（未实现 `prompt` 面）；推理模块占 104/120 字符 | 0 字符/轮 |
| 易变上下文 | 记忆模块**零贡献** | 0 |
| 工具描述 | `omb_recall` 222 字符（触发句开头）、`omb_forget` 63、`omb_remember` 92、`omb_relate` 166 = **543 字符**（约 350–450 token [推测]） | 固定/轮 |
| 工具 schema | 6+2+2 个参数（JSON Schema，随工具清单每轮发送） | 未逐字节测量 [推测] 与描述同量级 |
| 召回结果 | 全文 + 溯源，实测 5 条 = **3,877 字符**（≈2.4–3.2K token） | 每次召回 |
| 写入回执 | 成功 4–6 行（含 240 字符回显），弃权 2 行；实测单次 ~300–600 字符 | 每次写入 |

**结论**：记忆的"每轮固定成本"很小（~0.5K token），**单次召回的边际成本很大**（2.4–3.2K token）。当前设计把成本放在"模型主动拉"上是对的，但**拉回来的东西又长又不准**（§1.8），单位 token 收益极低。

### 3.2 证据质量（这一段决定上面数字怎么用）

- **所有竞品榜单数字都是作者自报**，我没有复现任何一个。r6 §3.6 找到的唯一独立复现项目（`agent-memory-almanac` 的 "published-vs-reproduced"）**全部 pending**。
- **MemoryBench 作者自己说**："the effectiveness and efficiency of state-of-the-art baselines are far from satisfying"（摘要原文）——即"现有 SOTA 在持续学习口径上普遍不行"，这与 OMB 实测的 36% 弃权率、检索精度塌陷是同一类问题，不是 OMB 独有的落后。
- **mem0 从图退回 ADD-only**（r6 §3.3 源码级）是"图不是必然演进方向"的最强反例；OMB 的 `edge` 机制保留即可，**不要因为别人建图而扩建图**。
- **可复现性最好的一条**：LongMemEval 的优化项（session decomposition / fact-augmented key / time-aware expansion）是**方法级**而非产品自报，且其"三阶段"口径可直接用于 OMB 自评。

### 3.3 可抄 / 不可抄（一句话版）

**抄**：多信号融合里补"实体/键扩展"；time-aware 查询扩展；snippet-first 召回；离线预算只投"可预测查询"；双时间轴字段语义。
**不抄**：写入时 LLM 抽取（Mem0/A-MEM/Zep 都要）、社区摘要（GraphRAG/Graphiti）、三级层次（MemoryOS）、六类记忆（MIRIX）、HyDE（需 LLM）。
**理由统一**：OMB 的约束是"热路径零 LLM、常驻 120 字符、当前 71 行存量"。凡是"用 LLM 换质量"的方案，在 71 行规模上都先用测量证明基线，否则是在给自说自话建索引。

### 4.2 因此，OMB 记忆应当「留 / 让 / 删」

| 能力 | 判断 | 理由 |
| --- | --- | --- |
| 原始会话历史（谁在何时说过/调用过什么、工具结果原文、错误、待办） | **让给 DSH** | 它已索引了 OMB 根本读不到的历史（`tool/result` 全文），且带血缘（trace）与精确读取（event_read）；OMB 再存一份是重复且必然不同步 |
| OMB 的 `episodic` 记忆（"本会话做了什么"的回顾） | **删掉写入路径** | 项目库里正是这类回顾体（3/3 行）；它们与宿主日志重复，且是垃圾召回的主要来源（§1.8d 的 hub 记录） |
| **中文语义/子串召回** | **留在 OMB** | DSH `unicode61` 实测不能做中文子串匹配；OMB 的 bigram FTS 是当前**唯一**可用的中文检索通道（§8 实验：`"记忆"` 命中 1 条、`"写入准入"` 命中 3 条） |
| **跨项目（用户级）知识** | **留在 OMB** | DSH 工作区授权是精确 cwd，跨项目检索在授权层就被拒；用户库是唯一跨项目面 |
| 结论的**有效性与溯源**（被取代/冲突/逐字保真） | **留在 OMB** | DSH 只有原始事件，没有"这条结论已被推翻"的语义 |
| 图/多跳 | 留在 OMB（维持现状，不扩建） | 已有 `edge`+`walkGraph`，在 1 条边的数据规模上无需变更 |
| 会话内"刚才说过什么" | **让给 DSH**（`session_event_search` 含当前会话） | OMB 的项目库召回在这个场景更慢且更差 |
| 召回触发 | **必须自建** | DSH 的 5 个工具不会替 OMB 触发；且 DSH 的 `session_search` 排除本会话，无法替代"本项目既往结论" |

### 4.3 token / 缓存成本对照

| 面 | OMB 记忆 | DSH 会话检索 |
| --- | --- | --- |
| 每轮固定 | 工具描述 543 字符（无常驻段） | 固定提示 **315 字符** + 5 个工具 schema |
| 单次结果 | 3,877 字符（5 条全文） | 每条命中 title + ≤240 码点 snippet；`maxSearchResults` 默认 100（可配小） |
| 缓存影响 | 工具定义不变 → 前缀稳定 | 固定提示 + schema 不变 → 前缀稳定；**bundle 开关会一次性失效前缀**（README §KV Cache） |
| 结论 | OMB 每次召回更贵但带有效性语义；DSH 每次更便宜但只有原文 | **两者不是替代关系**：OMB 应把"原文/回顾"让出去，把"结论"做短做准 |

## §5 重构提案（按 影响/成本/风险 排序）

> 统一约束：常驻预算 120 字符（已用 104）；工具面已有 10 个（规划上限 8）；热路径零 LLM；schema 只允许加法迁移；任何新能力优先做成已有工具的参数，不新增工具。

### P0 —— 修触发：让模型在"该查"时知道要查（影响高 / 成本极低 / 风险低）

**问题**：M1。记忆模块对模型完全不可见，只有 222 字符的工具描述。

**方案（两选一，A 优先）**
- **A. 借用 16 字符常驻余量（需与推理模块协商）**：推理模块常驻提示有短变体（`modules/reasoning/methods.ts:173-178`）。把长变体 104 字符换成短变体（实测 71 字符，`tests/dsh/prompt-injection-live.test.ts:49` 注释记录过 71），腾出 ≥33 字符；记忆模块新增一句 **≤24 字符**的常驻提示，例如「跨会话结论用 omb_recall 查」。**每轮固定成本 +24 字符（≈16 token [推测]），逐字节稳定，不破坏缓存。**
- **B. 不改常驻**：把 `omb_recall` 描述再压缩到 ≤160 字符，并在描述里点明「本仓库/本项目的既往结论只在这里」。**0 新增 token**，但触发效果弱于 A。

**文件级改动**：`modules/memory/index.ts`（manifest 增加 `prompt: { resident }` 或 `context` 空实现）、`modules/reasoning/methods.ts`（换变体）、`tests/dsh/resident-budget.test.ts`（断言合计 ≤120 且两项都在）、新增 `tests/modules/memory/resident-hint-stable.test.ts`（逐字节稳定）。

**验收（before/after，同一口径）**：以 391 会话基线 `omb_recall=52/391=0.133 次/会话`、有记忆的工作区中 27/391 有召回为 before；上线后跑 20 个新回合、10 个"延续类"任务，要求**有召回会话占比 ≥30%**，且 `Sandboxie-Plus`、`desktop-notify` 这两个"写而不读"的工作区至少各出现 1 次召回。**判死线**：20 回合内新增召回 <5 次 → 回退（删 resident 行）。

**风险/回滚**：唯一风险是与推理模块争预算 → 用测试钉住合计；回滚 = 删一行 manifest 字段 + 恢复推理变体。

### P1 —— 修写入：让"依据"可核验、让"回顾"进不来（影响高 / 成本中 / 风险中）

2. **废掉 `execution:` 前缀自证（修 M3），改为"真实执行台账"**：`dsh/session.ts:826-841` 已经对每次 `tool/call` 做指纹（工具名+参数摘要）。把"真实执行过的命令/测试结果"按会话记成一个小台账（内存即可，最多 100 条），`decideAdmission` 的 `execution-confirmed` 分支改为**要求 sourceRef 中的命令摘要能在台账里命中**；否则弃权。

### P2 —— 修检索精度与输出成本（影响高 / 成本中 / 风险低）

1. **词法通道加最低分 + 长度惩罚（修 M6/M7）**：`store.searchLexical` 返回 `-bm25` 分，在 `retrieve.ts` 融合前加一道 `score < 阈值` 过滤（阈值从**真实 53 条召回**的分数分布标定，不拍脑袋）；或改用 BM25+ 的 `b` 参数调整（SQLite FTS5 支持 `bm25(memory_fts, w1..wn)` 列权重，但没有 b 参数——**因此只能做后置分数过滤**）。
2. **召回改 snippet-first（修 M8）**：`renderRecall` 每条只给 **≤240 字符**摘要 + `id`；新增 `omb_recall({ ids?, full? })` 或 `detail: 'snippet' | 'full'`（默认 snippet）让模型按需取全文。**默认 5 条输出从 3,877 字符降到约 1,400–1,600 字符（−60%）**，每次召回省 ~1.4–1.9K token [实测模拟 + [推测]换算]。

**验收**：
- 输出成本：5 条召回字符数 3,877 → ≤1,600（脚本可复算：同一 5 行 DB 夹具）。
- 精度：用**真实 53 条查询**建回归集（查询 + 人工标注 top-1 是否切题），当前人工判读约 **30%**（13/43）；目标 ≥60%。零命中率不上升（before 5/53）。
- `mode: always` 下 pressure-tight 不再伪装成"没有"。

**文件级改动**：`modules/memory/retrieve.ts`（分数下限/时间扩展）、`store.ts`（可选返回 length 供惩罚）、`recall.ts`（snippet 渲染 + `mode`/`detail` 参数）、`tests/modules/retrieval/*`、新增 `tests/modules/memory/recall-snippet-budget.test.ts`。

**风险/回滚**：snippet 会让模型偶尔需要二次拉取（多一次调用）；用 `detail:'full'` 兜底。回滚 = 参数默认值改回 `full`。
