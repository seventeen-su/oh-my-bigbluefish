## 0. 一页结论

1. **这个组件没有"行为"，只有"报表"**：生产代码里唯一在跑的是 `recordPull`（每个工具结果记一次数）与 `omb_status` 的组件段落。`admission`（准入）、`select`/`marginalValue`/`measuredCost`、`pushLimit`/`indexOnly`/`announcePressure` 全部零生产消费者；模块没有模型可见工具、也没有任何 `prompt:` 贡献。`[源码]` `dsh/session.ts:843-870`、`modules/context/index.ts:492-533`、`modules/context/tools.ts:31-34`。
2. **它在 token 账上可以忽略不计**：全机 391 个会话、39,142 次请求、累计 11.98 B prompt token；上下文段落平均 483 字符、模块健康行 133 字符，68 次 `omb_status` 合计约 4.2 万字符 ≈ 4.2 万 token —— **占全部 prompt token 的 0.00035%**。每回合增量 = 0。`[实测]`
3. **行为侧同样可忽略**：49,440 次工具调用中 `omb_recall/relate/files/method/focus` 合计 216 次（0.44%）；五个视图的"杀死判据"若真的接线执行，会在任何 ≥20 轮的会话里把五个工具全部判死（全库 216 次 / 39,081 step = 0.0055 次/step，远低于判据 0.05 次/轮）。`[实测]` `modules/context/watch.ts:20,41-44,230-233`
4. **压力读数有一个决定性缺陷：`dsh/pressure.ts` 把"投影的宿主 state"当"客户端 wire view"读**。`stateOf` 返回的是 host state（`session-projection/src/index.ts:313-328`），而代码按 view 形状取字段：`projectedTokens` 不在 host state 里（永远回落到 `pressureTokens`）、`tokenUsage` 的 host state 是 `{totals,last}`（所以缓存读写永远 0）、`contextBreakdown` 的 host state 是 `{systems,surfaceTokens,breakdown}`（所以"最贵块"永远为空）。`[源码]` `dsh/pressure.ts:226-263`、`usage-projection.ts:56-64,96-108,149,208-216`、`breakdown-projection.ts:53-59,186`
5. **这解释了 Lead 看到的"pressure 0.021 vs reasoning tight"**：06:39:22 那一次请求组装时，桥读到的是 `pressureTokens`（压缩前最后一次 provider 上报 = 615,831，fillRatio 0.616 → tight）；6 秒后 `omb_status` 读到的是第一次响应 usage 更新后的 21,308（0.021 → relaxed）。不是两个压力源，是**同一读数在压缩后"晚一拍"**。`[实测]`（会话 `session-40edda4c`：06:13:35 prompt 615,831；06:18:54 用户 `/compact`；06:19:17 摘要输入 616,209 / 遮蔽 464,011；06:39:22 首个新请求；06:39:28 响应 prompt 21,308；同一状态里 reasoning trace 写 `压力 tight`，顶层写 0.021）。
6. **状态面存在稳定的自相矛盾**：68 份 `omb_status` 里 **68/68** 的模块健康行写 `fillRatio 未知（未测量）`，其中 9 份同一份输出的组件段落却有精确 fillRatio（0.095/0.413/0.523…）；**21/68** 的"拉取台账：未知会话"同一段里却列出当前会话的 bucket。`[实测]`
7. **"未知会话"不是记错账，是不肯显示账**：`panelInput` 的主行固定调 `snapshotFor()`（不传会话），于是永远渲染"未知会话桶"；每会话的桶其实记在下面（`modules/context/index.ts:564-582,573`）。`[源码]`
8. **宿主已经做了的事，它做不了、也不该重做**：压缩（`compaction-basic`，默认 0.8/0.16/65,536）、工具结果裁剪（`tool-result-pruner`，8192/4096/1024）、token 计量（`token-meter`）、会话检索（`session-search` 五工具）都在宿主。全机 35 次压缩、342 次 prune 是既有事实；压缩的**摘要调用输入 17.8 M token，缓存读只占 1.17%，输入/释放比中位 1.417** —— 压缩很贵，正确策略是少触发它，而不是再造一个。`[实测]` `[源码]`
9. **总判据**：这不是"差一点接上"的功能，而是**一个没有生产者的裁决 API + 一个没有消费者/渲染器的推送协议 + 一张永远读错形状的度量桥**。最小修法（修投影形状、修状态口径）能立刻让读数变真；终局建议是 **删组件、把残余价值折进 `omb_status` 顶层与工具描述（JIT）**，见 §4。
10. **给用户的一句话**：上下文优化当前的真实价值 ≈ 0，但它制造了 1,745 行代码、1,601 行测试、0.00035% 的 token 账单和一份会自我矛盾的唯一模型可见诊断入口。先把它变成"说真话的小组件"，再决定是否值得留。

### 1.2 压力：从 provider 到 band 的完整链路（含形状缺陷）

```
provider usage（assistant/message.usage）
  → token-meter contextPressure 投影（host state: {contextWindow, pressureTokens, surfaceTokens, sampledSurfaceTokens, claim?}）
  → ctx.sessionProjections.stateOf(session, 'contextPressure')   // 返回 host state
  → dsh/pressure.ts measure() 读 pressure['projectedTokens'] ?? pressure['pressureTokens']   // ← projectedTokens 不存在！

  → 状态面 / 提示注入
```

- `[源码]` `dsh/pressure.ts:226-263`：先 `projectionOf(KEY_PRESSURE)`，`total = firstFinite(pressure['projectedTokens'], pressure['pressureTokens'])`（:235），`window = contextWindow`，`fillRatio = total/window`（:255）。
- `[源码]` `session-projection/src/index.ts:313-328`：`stateOf` 的文档与实现都是**host state**；wire view 是另一条路径（`wire.view`）。
- `[源码]` `usage-projection.ts`：`contextPressureStateSchema` 只有 `{contextWindow, pressureTokens, surfaceTokens, sampledSurfaceTokens, claim?}`（:96-108）；`projectedTokens` 只在 `wire.view` 里由 `pressureTokens + surfaceTokens − sampledSurfaceTokens` 算出（:210-216）。
- **后果 A**：`projectedTokens` 永远读不到 → 永远回落到 `pressureTokens`（上一次请求的真实 prompt 大小）。但"下一次请求"的读数恰恰要靠 `projectedTokens`：它在 surface 被 compaction 缩小的当刻就下降，而 `pressureTokens` 要等下一次 provider usage。`dsh/pressure.ts:232-234` 的注释写明了这个意图，代码却没有做到。
- **后果 B**：`tokenUsage` 的 host state 是 `{totals,last}`（`usage-projection.ts:56-64`），`dsh/pressure.ts:260-261` 取 `usage['cacheReadTokens']` 恒 `undefined → 0`，于是状态面永远写"缓存：读 0 / 写 0（未测量）"。实测反例：同一会话 step 28 的 usage 是 `cacheReadTokens=104,704`。`[实测]`
- **后果 C**：`contextBreakdown` 的 host state 是 `{systems,surfaceTokens,breakdown:{systemTokens,toolsTokens,messageTokens}}`（`breakdown-projection.ts:53-59`），`dsh/pressure.ts:192-203` 在顶层取 `systemTokens/toolsTokens/messageTokens` 全部 `undefined`，`nodes` 恒空，状态面"最贵 N 块"从未出现。`[实测]`（68 份 status 均无该行）
- **后果 D（Lead 的问题）**：模块自身的 `pressureOf(session)` 与顶层 `renderStatus` 都走同一个 `kernel.pressure`，所以 0.021/21,308 在"压缩后第一次响应之后"是**同一个数**；reasoning 的 `lastRender.band=tight` 是**上一次渲染的输入快照**（`modules/reasoning/index.ts:572-690`，`band: input.band`），而 06:39:22 那次组装仍读到 615,831（压缩前的最后一次 provider 上报），因为 `projectedTokens` 读不到。它不是第二套压力，是**同一投影的旧采样**。权威口径 = `kernel.pressure` 在"压缩后的下一次 provider usage 之后"的读数；`lastRender` 只是历史，且当前缺时间戳/序号，无法自证新旧。
- **后果 E（模块健康行的"fillRatio 未知"）**：不是 stale，而是**结构性未测量**。`healthNow()` 调 `pressureOf()`（`index.ts:371-410`，`pressureOf` 见 :285-300），而 `resolveSession(undefined)` 恒返回 `null`（`index.ts:264-267`），于是恒走"无会话"分支：`{fillRatio:null, band:'relaxed'}`（:292）。同一个 `omb_status` 里，组件段落由 `panelInput(session)` 带会话渲染（`dsh/status-tool.ts:201-205,360-373`），所以一边是 0.021、一边是"未知/relaxed"。68/68 次如此。`[源码]`+`[实测]`

### 1.3 准入为什么零消费者（不是"等接线"，是两侧都缺）

- 没有**生产者**：没有任何模块构造 `Candidate`（id/text/relevance/tokens/depths）交给 context 模块；`admission.ts` 的 import 只出现在 `modules/context/index.ts` 与测试。
- 没有**渲染器**：即使有人调 `select` 拿到一条候选，也没有路径把它写进提示或工具结果；`BandBehavior` 的 `pushLimit/indexOnly/announcePressure` 只被 `tools.ts`/`index.ts` 的状态面读。`pressure.ts:34,45,76,86` 自己用注释写明"无调用方"。
- 唯一"看起来像接线"的字段 `ContextRenderInput.band` 是**宿主**传给所有提示贡献者的（`dsh/session.ts:641-645`），消费者是 `modules/reasoning/index.ts:572+` 与 `modules/profile/index.ts:548` —— 这是"压力真的塑形"的唯一生产通路，但它属于宿主/推理，不属于 context 模块。
- 所以"如果消费者存在，它会做什么"：moderate 档按 `(relevance×novelty)/cost` 贪心推 1 条；tight 档只给索引 + 主动提示"上下文紧张"（`pressure.ts:57-88`）。**前提是**有人提供候选、有人把返回值渲染进上下文；两个前提都不存在。接上它等于新建两条链路，而不是补齐一条线。

### 1.4 拉取台账为什么"认不出会话"

- 记账本身是分会话的：`recordPull` 从 `exec.agent.session.id` 取会话（`dsh/session.ts:843-848,861-866`），空则落 `UNKNOWN_SESSION_KEY`；`turn/start` 由 `step/start` 映射（`dsh/session.ts:798-809`），带 `sessionId`。
- **"未知会话"是渲染选择**：`panelInput` 的主行 `pulls: snapshotFor()` **不传会话**（`index.ts:573`），`snapshotFor(undefined)` 用 `sessionKeyOf(null)`（`watch.ts:31-33`）落进未知桶；而每会话桶在 `sessionsSnapshot()` 里照常列出（`index.ts:328-344`）。因此同一段里出现"未知会话拉取 0 次/轮数未知"+"`- session-40edda4c…：0 次 / 1 轮"。
- 数据层没有跨会话污染；`turns` 也确实是该会话的（`index.ts:439-451`）。**结论：Lead 看到的"cannot identify current session"是面板不肯选会话，而不是记不到。**`[源码]`+`[实测]`（21/68）

### 1.5 `behavior none` 是什么意思

- 当前 band = relaxed（0.021/0.413/0.523 都落在 [0.3,0.6) 之外或之内按阈值），relaxed 的行为表是 `mode:'none', pushAllowed:false, pushLimit:0, indexOnly:false, announcePressure:false`（`pressure.ts:57-67`）。
- 它只影响**状态文本**："档位行为：none，最多推 0 条，不做主动推"。由于 `select` 零调用方，即使 band=moderate 也不会真的推 1 条；`indexOnly/announcePressure` 在 tight 也不会发生（`pressure.ts:40-46,76,86` 自己承认）。
- 真正会改变模型输入的是 `ContextRenderInput.band` 对 reasoning 的作用：`controlForBand` 在 tight 时抬升证据/收尾门槛（`modules/reasoning/control.ts:126-145`），但 standard 深度下 `injectCard=null`、`controlText=''`（本次 status 的 reasoning 自述"上次注入：空"就是它）。也就是说：**压力→行为的唯一真实通路在 tight+deep 时才会改变文本，而本次是 standard+（压缩前）tight，实际注入为空。**`[源码]`+`[实测]`

## 2. SOTA 调研（2025-2026）

### 2.1 上下文会退化（context rot / lost-in-the-middle）

- **Chroma《Context Rot》**（2025-07-14，18 个模型，含 GPT-4.1/Claude 4/Gemini 2.5/Qwen3）：即使任务难度不变，输入变长也会让表现**非均匀下降**；语义相似度低的 needle-question 退化更快；干扰项（distractor）的影响随长度放大；**打乱叙事结构的 haystack 反而更好**（结构化上下文可能更伤）。LongMemEval 子实验：全长 ~113 K vs 聚焦 ~300 token，聚焦显著更好。结论：**"相关且短"胜于"全且长"**，且"加了上下文"本身会引入检索负担。`[报告]` <https://www.trychroma.com/research/context-rot>
- **Lost in the Middle**（Liu et al., TACL 2024）：相关信息在开头/结尾时最好，在中间显著退化，呈 U 形；即便宣称长窗口的模型也如此。含义：**不要靠"塞进去"解决召回，要靠"放在对的位置/按需取"**。`[报告]` <https://aclanthology.org/2024.tacl-1.9/>
- 对 OMB 的直接含义：`admission` 的"选一条推给模型"在最优情况下也只是把"检索"从模型手里拿走，而证据显示**模型自己按需拉取（JIT）**通常更稳；尤其在没有相关性标注、没有评测集的插件里，推送很容易变成干扰项。

### 2.2 前缀缓存/前缀稳定（prompt caching）

- **Anthropic Prompt Caching**：缓存前缀需显式 `cache_control`，读缓存价格约为写入的 1/10，写入有 5 分钟/1 小时 TTL；**前缀任何变化都使其后的缓存失效**。`[报告]` <https://platform.claude.com/docs/en/build-with-claude/prompt-caching>
- **DeepSeek Context Caching**：磁盘前缀缓存**默认开启**，按"完整匹配的 cache prefix unit"命中；会按用户输入边界、模型输出边界、固定 token 间隔切 prefix unit；**"best-effort"，不保证 100%**；构造需要数秒，闲置几小时到几天清除。`[报告]` <https://api-docs.deepseek.com/guides/kv_cache>
- 机制含义：**前缀越稳定、越长，越便宜**。任何"每轮变化的系统提示/动态段"都是缓存缝。这既否定了"每轮按压力注入不同内容"的方案，也解释了 OMB 常驻提示要"逐字节稳定"（`dsh/session.ts:249-261`）。
- 本机反例（提醒不要假设缓存一定命中）：35 次压缩的摘要调用 17.8 M 输入 token 里，`cacheReadTokens` 只有 208,768（**1.17%**）。`[实测]` 这与 `compaction-basic` README 宣称的"复用 warm prefix"不符，可能和 `/compact` 前的空闲、路由/工具投影变化有关；无论如何，**不能把缓存命中当默认**。

### 2.3 压缩/摘要（Anthropic、Claude Code、Cursor）

- **Anthropic《Effective context engineering for AI agents》**（2025-09-29）：把上下文当有限"attention budget"；推荐 compaction、structured note-taking、sub-agent 三种长任务策略；Claude Code 的压缩是"摘要历史 + 保留最近访问的 5 个文件"；**tool result clearing 是最轻的压缩**（已被平台化为 context management 功能）。`[报告]` <https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>
- **Claude Code**：`/compact` 手动 + 接近窗口时自动压缩；`autoCompactWindow` 可在设置里指定自动压缩的窗口阈值（文档 `model-config`）。SDK 文档：窗口接近上限时自动压缩旧历史。`[报告]` <https://code.claude.com/docs/en/model-config>、<https://code.claude.com/docs/en/agent-sdk/agent-loop>
- **Cursor**：`Dynamic context discovery`（2026-01-06）：长工具输出写文件、摘要时给历史文件引用、Skill 只带 name/description、MCP 工具描述同步到文件夹按需查、终端输出当文件；A/B 中"调用了 MCP 工具的 run"总 token **下降 46.9%**。`[报告]` <https://cursor.com/blog/dynamic-context-discovery>
- **学术侧**：`The Complexity Trap`（NeurIPS 2025, arXiv:2508.21433）报告 observation masking 与 LLM 摘要效果相当而成本约一半；与 OMB 前序报告 `D:\Program\omb-wt\_research\context-compression.md` 的结论一致。`[报告]` <https://arxiv.org/abs/2508.21433>
- 对本机的量：35 次压缩、12.58 M 被遮蔽 token、17.81 M 摘要输入 token、146,742 摘要输出 token；**输入/释放比中位 1.417，最小 0.881，最大 5.907**（中位 >1 ⇒ 至少一半样本是净花 token；与前序 r3 报告的 21/22 一致）。`[实测]` 这说明"压缩"在当前配置下**经常是净花 token**（换来的是未来请求变短，不是即时省钱），所以最优策略是**减少触发压缩的频率**（短工具输出、按需读取），而不是自造压缩器。

### 2.4 上下文预算管理 / 即时检索（JIT）/ 渐进披露

- Anthropic：JIT 检索——维护轻量标识（路径、查询、链接），运行时用工具取；progressive disclosure；file system 的层级/命名/时间戳本身就是信号。`[报告]` 同上。
- Cursor：dynamic context discovery（同上）；MCP 工具"先给名字，按需读描述"。
- 对 OMB：**架构方向本来就对**——记忆/规则卡/文件索引全是工具拉取，常驻提示只放一句触发语（`docs/context-budget.md` 的结论：把"何时用"写进工具描述，93 字符，已落地）。上下文模块不需要再发明"推送"，它需要的是**让拉取更容易被想到**（工具描述/技能目录）与**让拉取结果更短**（工具返回格式）。

### 2.5 动态工具加载 / tool search

- **Anthropic《Introducing advanced tool use》**（2025-11-24）：Tool Search Tool 让工具定义延迟加载（`defer_loading: true`），示例里工具定义从 ~55 K token 降到 ~8.7 K（**−85%**），准确率 Opus 4 49%→74%、Opus 4.5 79.5%→88.1%；**延迟加载不破坏 prompt caching**（不进入初始 prompt）；建议保留 3-5 个最常用工具常驻。`[报告]` <https://www.anthropic.com/engineering/advanced-tool-use>
- 对 OMB：这是"工具目录变大后"的正解；当前 OMB 工具 10 个、schema 不算大，**不需要自造 tool search**；但应记住原则——**工具定义是每轮成本，数量与描述长度都要控制**。上下文模块没有工具，正好符合"少而准"。

### 2.6 子代理上下文隔离

- Anthropic：sub-agent 用干净上下文深挖，只回传 1,000-2,000 token 的浓缩结果；这是长任务的三种主策略之一。`[报告]` 同上。
- DSH 原生：子代理有独立 Session、`subagent/catalog` 只进日志、父侧只收完成通知；`list_children` 不读子日志（`packages/subagent/subagent/README.md:59-125,161-191`）。`[源码]`
- 对 OMB：**真正的"上下文优化"杠杆是"把工作放进子代理"**（隔离 + 只回传结论），而不是在主会话里做准入/塑形。这是 context 组件应当让位的地方。

### 2.7 KV-cache 复用 / attention sinks（StreamingLLM、H2O、SnapKV）

- **StreamingLLM**：保留最初 4 个"attention sink" token + 最近窗口，可流式处理 4 M token，比滑窗重算快 22.2×。`[报告]` <https://hanlab.mit.edu/projects/streamingllm>
- **H2O**：按 attention 的 heavy hitters 保留 KV，20% 预算即可超过 full-cache 吞吐（相对 DeepSpeed 最高 29×）。`[报告]` <https://proceedings.nips.cc/paper_files/paper/2023/hash/6ceefa7b15572587b78ecfcebb2827f8-Abstract-Conference.html>
- **SnapKV**：用 observation window 的 attention 选重要 KV，3.6× 生成加速、8.2× 内存效率。`[报告]` <https://neurips.cc/virtual/2024/poster/93531>
- **与本插件的关系：不可用**。这些都需要改模型/推理栈的 KV cache 管理；OMB 是 Cordis 插件，拿不到 attention、也改不了 serving。它们唯一可迁移的**类比**是"保留头尾、裁中间"——而这已经被宿主 `tool-result-pruner` 以确定性方式做了（head 4096 / tail 1024 / marker）。`[源码]` `packages/compaction/compaction-tool-result-pruner/src/config.ts:9-16`
- 因此：**任何"KV cache 复用/驱逐"方案对 OMB 都是噪音**，不列入设计选项。

### 2.8 与"插件不能改模型"这一约束无关/相关的分界

| 技术 | 需要改模型/推理栈？ | 对 OMB 可用性 |
|---|---|---|
| context rot / lost-in-middle 的**结论** | 否 | 可用（设计原则） |
| prompt caching / prefix 稳定 | 否（provider 侧，插件只需保持前缀稳定） | 可用（约束） |
| compaction / 摘要 / observation masking | 否（宿主已实现） | 宿主侧；OMB 只读 |
| JIT 检索 / progressive disclosure / tool search | 否 | 可用（工具描述/索引） |
| 子代理隔离 | 否（宿主已实现） | 可用（委派策略） |
| StreamingLLM/H2O/SnapKV | **是** | **不可用** |
| tokenizer 级压缩（LLMLingua 等） | 需要模型侧解码/再训练或额外模型 | 不可用（本插件无模型调用预算） |

## 3. DSH 0.2.1-rc.2 原生上下文能力与集成边界

### 3.1 compaction（宿主已有，OMB 不该重做）

- **契约**：`ctx.compaction` 服务；三个操作 `compactIfNeeded/compactNow/compactRegion`；结算 = 把 surface 区间替换成**一个摘要节点**，日志追加 `compaction/start`/`compaction/summary`/`compaction/end`（log-only），摘要节点带 `<compacted-summary>`；一个 context 只能挂一个实现。`[源码]` `packages/compaction/compaction/README.md:67-115`、`src/types.ts:17-120`
- **默认后端**：`compaction-basic` 在 `agent/pre-step` 按压力触发，`agent/request-error` 对 `CONTEXT_WINDOW_EXCEEDED` 兜底；默认 `thresholdRatio 0.8`、`retainRatio 0.16`、`headroomTokens 65,536`；阈值 = `floor(min(W×0.8, W−O−B))`。窗口 1 M、输出预留 256 K 时 ≈ **678,464 token**。`[源码]` `compaction-basic/src/config.ts:20-23,75-78,153-217`、`src/index.ts:158-205,292,319`
- **模型侧**：压缩是 `/compact` 人工命令 + 自动压力，**没有模型可见的压缩工具**（`README.md:159`）。
- **本机实测**：OMB 预设把 `compaction-basic` 挂在 `preset-omb` 的 `compaction` 组里（`D:\Program\Oh-My-BigBlueFish\cordis.patch.yml:216-232`），使用默认阈值；组带 `isolate: {compaction:true, toolResultPruner:true}`。全库 35 次压缩、7 次显式 `/compact`；本次 `/compact`：摘要输入 616,209 token、输出 3,279、被遮蔽 464,011、耗时 23 s、`cacheReadTokens=0`。`[实测]`
- **集成结论**：不要替换、不要并行实现（会双压；且隔离组让补丁层按 id 够不到实例，前序报告 `context-compression.md` 已记录 #1772 同类坑）。OMB 能做的只有：**读 `compaction/*` 日志事件**（log-only，`packages/core/session/src/known-event-types.ts:32-35`）做事实报表；以及在用户面前**建议何时 `/compact`**（压缩是人工命令，见 §4-B）。
- **顺带发现的可乘之隙**：宿主 `tool-result-pruner` **只在压缩触发后才运行**（`compaction-basic/src/index.ts:292` 取 `toolResultPruner`；README:60 "Trimming only runs when a compaction trigger qualifies"）。自动压缩阈值约 0.678（1 M 窗口、256 K 输出预留、65,536 headroom）之前——即 fillRatio 0.6 到 0.678 的"软紧张"区间里，宿主既不裁也不压；这是 OMB 唯一可能插入"确定性减负"的窗口——但 OMB 不能改会话历史，只能改变**模型下一次怎么写**（提示/工具描述），或提醒用户。

### 3.2 会话投影（session projections）契约

- 注册单位 `ctx.sessionProjections.register(...)`；`stateOf(session, key)` 返回 **host state**（`session-projection/src/index.ts:226-328`）；client view 是 `wire.view` 的另一条路径。三个关键投影：
  - `contextPressure`：host state `{contextWindow, pressureTokens, surfaceTokens, sampledSurfaceTokens, claim?}`；wire view 才含 `projectedTokens = pressureTokens + surfaceTokens − sampledSurfaceTokens`（`llm/token-meter/src/usage-projection.ts:96-108,208-216`）。
  - `tokenUsage`：host state `{totals,last}`；wire view = `totals`（同上 :56-64,149）。
  - `contextBreakdown`：host state `{systems,surfaceTokens,breakdown:{systemTokens,toolsTokens,messageTokens}}`；wire view = `breakdown`（`breakdown-projection.ts:53-59,186`）。
- **这是 §1.2 缺陷的直接证据**。修复只需在 `dsh/pressure.ts` 顶层读对嵌套字段，或走 client view（若可达）。token-meter 自己的 estimator 是 4 字符/token、**明确承认低估 CJK/JSON schema 3-4×**（`llm/token-meter/src/estimate.ts:12-13`、`projection.ts:50-57`），所以 OMB 不应该自己再算 token；用 provider usage 与 host view。
- 另：`contextWindow` 只从 `request/context` 来（本次实测 1,000,000，`session-40edda4c` 04:28:28 事件）；切模型时新旧字段可能不同步（projection.ts:20-29 明确说不是原子观测）。

### 3.3 tool-result-pruner（宿主已有）

- 默认：`thresholdChars 8192`、`headChars 4096`、`tailChars 1024`；marker `[... tool result middle pruned ...]`；只在压缩触发后运行；替换 `tool/result` + 前置 `compaction/prune` shadow price。`[源码]` `compaction-tool-result-pruner/src/config.ts:9-16,48-60`、`README.md:44-60,116-120`
- 全库 **342 次 prune**、35 次压缩 → 平均每次压缩前裁 9.8 个结果。`[实测]`（census）
- 对 OMB：**不要做 observation masking**——宿主已经做了确定性版本，且只在需要时做。OMB 若在 0.6–0.8 区间自己"建议模型缩短输出"是可行的软手段；直接改内容是拿不到缝的。

### 3.4 session-search 作为"外置上下文"：可行性、成本、冷启动

- 组成：`@deepseek-ai/dsh-session-query-sqlite`（FTS5）+ `@deepseek-ai/dsh-tool-session-query`（5 个模型工具：`session_search`/`session_event_search`/`session_trace`/`session_event_trace`/`session_event_read`）。`[源码]` `experimental/tool-session-query/README.md:43-53`
- 本 profile 的启用方式：`optional-session-search` 组，**`isolate: {sessionQuery: true}`**，sqlite 配置 `path: ':memory:'`、`openAt: first-search`（`packages/experimental/session-search/cordis.patch.yml`）。
- **冷启动实测**：`session_search` 4 个并行调用全部 30 s 超时（`searchTimeoutMs` 默认 30000）；全库 391 个持久会话、283 MB 压缩日志、256 K 事件；全库历史上 `session_search` 仅 6 次调用。`[实测]`机制：`session-query-sqlite` 每次搜索执行一次**串行 reconciliation**，要列出 persistence snapshots、逐会话比较 revision、读新/变更日志、抽文档、在一个事务里提交；`:memory:` 索引在每次宿主重启后从零开始；`DatabaseSync` **同步执行并阻塞 JS 线程**，已执行的语句不可中断。`[源码]` `session-query/session-query-sqlite/README.md:31-37,104-113,140-146`
- **集成边界**：
  1. 根上下文里 `session-query-sqlite` 以 `openAt: never` 挂载（`packages/bundle/base/cordis.patch.yml:151-158`），即根服务的搜索是**禁用**的（`SESSION_QUERY_SEARCH_DISABLED`）；可搜索的实例在隔离组里，**OMB 从外部拿不到**。
  2. OMB 若要自己挂一个 sqlite 实例，会得到第二份索引（内存/磁盘 + 重复 reconciliation），且仍受"进程内同一路径单所有者"约束；`[源码]` README:140-146。
  3. 因此"把 session-search 当每回合外部上下文"不可行：冷启动 O(全部会话)、同步阻塞、30 s 超时、重启清零。**可行用法只有：模型显式调用（人工/任务驱动），且最好配 durable `path` + `openAt: startup` 把冷启动成本前移到启动期。**
- **对本组件的结论**：不要用 session-search 做自动注入；它的正确位置是**模型自己的工具**（已在，且有固定说明段与 5 个 schema 的每轮成本）。OMB 记忆库与它互补（跨工作区/长期偏好），不重叠（§memory 报告负责）。
