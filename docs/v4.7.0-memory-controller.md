# OMB v4.7.0 — 事件驱动记忆控制器

> 用户提出："事件驱动记忆控制器，除了主动提示记忆外，更安全更高效地提高 AI 记忆和
> 管理记忆主动性的做法。" 这是**一个功能**：阶段 1 先做确定性决策（dry-run），
> 阶段 2 在同一版本内让动作真正执行；不为阶段单独升版本号，`dry-run`/`off` 保留为
> 回滚开关。按 `x1.x2.x3` 纪律，整件事属于一次功能更新 → **4.7.0**。

## 1. 问题

现有主动性靠两层提示：

- 常驻提示："长期偏好/决定主动 omb_remember；跨会话结论先 omb_recall"；
- `proactive.ts`：用户消息命中信号时注入一行动态提示。

它们提高的是模型"注意到该记忆"的概率，但仍然：

- 模型可以忽略提示；
- 临时任务约束可能被写成长期偏好；
- 纠正旧结论可能没查旧 id 就写新条目；
- 每次提示都占上下文，而多数消息根本不需要记忆动作。

## 2. 控制器

新增纯模块 `modules/memory/controller.ts`：

```text
events: user-message / tool-result / turn-end / memory-written
          ↓  reduceMemoryEvent（纯函数，零 I/O、零时钟、零 LLM）
actions: persist | lookup | request-model | track-task | expire-task
```

状态按会话保存（有界）：

- `candidates`：候选记忆（最多 8；同文本去重）；
- `tasks`：当前任务约束（最多 8；TTL 2h + 回合结束双过期）；
- `lastEventAt`：最近事件时间（TTL 判定与诊断用）。

### 安全闸门（reducer 内硬编码）

| 输入 | 动作 | 理由 |
| --- | --- | --- |
| 显式"记住" + 长期边界 | `persist`（confirmed） | 用户明确要求，优先级最高 |
| 长期偏好/稳定决策（非显式） | `persist`（candidate） | 不冒充已确认 |
| 临时/任务约束 | `track-task`（TTL/回合结束 `expire-task`） | **永不** persist |
| 显式要求记住临时约束 | `request-model`（限定边界） | 人工决定作用域/失效 |
| 纠正旧结论 | `lookup` + `request-model` | 旧 id 未拿到前不写 supersedes |
| 工具结果 | 无动作 | 项目证据由 project-evidence 单独处理 |
| `memory-written` | 清除同文本候选 | 真实写入已覆盖 |
| 疑问句/命令/代码/无偏好标记/含密钥 | 无动作 | 不做记忆决策 |

判据只有一份：疑问/命令/代码/偏好标记在 `modules/memory/message-filter.ts`，
捕获路径与控制器共用，避免"控制器决定写、写入路径认为该跳过"的分裂。

## 3. 阶段 1：dry-run 接入

`capture.ts` 把每个用户消息、工具结果、回合结束喂给控制器，但只：

- 推进控制器状态并累计动作计数；
- 写入路径仍由原有 `capturePreference` / 准入 / 生命周期闸门决定；
- 计数经记忆健康面暴露：`capture.controller.events / persist / lookup /
  requestModel / trackTask / expireTask`。

这是现在的回滚档 `memoryController: dry-run`。

## 4. 阶段 2：执行

### 4.1 persist

| 输入 | scope | assertedBy | 生命周期阶段 | 每会话上限 |
| --- | --- | --- | --- | --- |
| 显式"记住" | 稳定决策→项目库；长期偏好→用户库 | `user` | 已确认 | **不受**上限 |
| 非显式长期偏好/稳定决策 | 同上 | `model` | 候选 | 受上限（默认 5） |

写入走既有路径：隐私闸门 → 库解析/冷启动重试 → 内存+库内去重 → `store.put` →
`memory/written` 事件 → 图自动连边。候选不冒充已确认：`lifecycle.ts` 按
`kind + assertedBy` 推导，召回回执会显示"候选"。

### 4.2 查回验证

写入成功后按 `record.id` 调 `store.getMany([id])`，要求 id 存在且 `contentHash`
一致，才计 `verified`；否则计 `verifyFailed` 并注入一行"不要重复写，先 omb_recall
核对"。**验证失败不等于写入失败**，两条计数分开报。

### 4.3 lookup

纠正消息触发跨项目库/用户库的**词法**检索（中文 bigram FTS；探针 = 整句 + 按标点
切开的片段，最多 4 个），命中后注入：

`检测到纠正：旧条目 id=…；核对后用 omb_remember(supersedes=["…"]) 写入新结论。`

未命中则注入"先 omb_recall 再写，不要直接覆盖"。**不自动 supersedes**：控制器无法
判断新陈述是否完整替代旧条目。热路径不加载嵌入模型。

### 4.4 任务约束

- 按会话保存；TTL 2h，任何事件到达时先清算到期任务（reason=`ttl`）；
- 回合结束无条件清空（reason=`turn-end`）；
- execute 模式下 `nudge` 兜底把活跃约束原文（≤80 字符）放进易变槽：
  `当前任务约束（回合结束失效）：这次不要联网，先离线测试`。

TTL 与状态面都按**事件时间**判定，不另取墙钟——reducer 没有时钟，两个时钟域不混用。

### 4.5 提示抑制

execute 且自动捕获开启时，**抑制 proactive 提示**：控制器已自己写/查/跟踪，再提示
"立即调用 omb_remember"会让模型把同一条内容写第二遍（库层没有正文唯一约束）。
`autoCapturePreferences=false` 时保留提示（控制器不写，模型仍需知道该主动记）。

## 5. 模式与回滚

`memoryController` 配置（`modules/memory/index.ts`，`cordis.patch.yml` 可覆盖）：

| 值 | 行为 |
| --- | --- |
| `execute`（缺省） | 动作执行 + 查回验证 + 提示注入 |
| `dry-run` | 只决策/计数，写入仍走旧捕获路径（阶段 1 行为） |
| `off` | 控制器完全不接入，回到 v4.6 的提示 + 捕获路径 |

## 6. 状态面

- execute：`事件控制器（执行）：N 事件 → persist A（写入 B/查回 C/验证失败 D/写路径拒绝 E）/lookup F（命中 G）/request H（注入 I）/track J/expire K；当前任务约束 L 条（回合结束失效）`
- dry-run：`事件控制器 dry-run：…（dry-run：只决策、不改写入路径）`
- off：`事件控制器：已关闭（memoryController=off）`
- 没有事件：`…：本进程尚无事件`（不写"正常"）

决策计数（`capture.controller.persist` 等）与执行计数（`persisted/verified/
verifyFailed/persistSkipped/lookupHits/requestInjections/tasksActive`）分开；
文案由导出的 `controllerHealthNote()` 生成，单测钉住"dry-run 不得出现写入计数"。

## 7. 明确未做（不要假装已做）

1. **不自动 supersedes**：旧 id 交给模型核对。
2. **任务约束不跨会话/进程**：进程重启即丢，临时约束本来就该丢。
3. **lookup 只走词法**：语义检索仍由 `omb_recall` 承担。
4. **候选不自动晋升**：只能由用户显式确认；手动入口 `/omb-confirm` 在 v4.8.0 提供
   （见 [`v4.8.0-lifecycle-confirm-and-dedupe.md`](v4.8.0-lifecycle-confirm-and-dedupe.md)）。
5. **无正文唯一索引**：v4.8.0 起控制器写入、捕获路径与 `omb_remember` 共用
   `findSameContent` 做精确同内容去重；近义改写仍由离线整合处理。
