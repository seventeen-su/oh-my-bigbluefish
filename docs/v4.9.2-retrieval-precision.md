# OMB v4.9.2 — 检索命中排名读数（precision@1/3/5）

> 这是既有"有效命中"读数的细化（x3），不是新功能：原来的
> `exposed/used/effectiveRate` 只知道"用过没有"，不知道**用的是不是排在前面**。
> 本版补上使用命中时的曝光排名分布，回答"检索把真正有用的条目排在前面了吗"。

## 1. 口径（先写清分母）

- 每当 `omb_recall` 返回结果，`usageTracker` 按**返回顺序**记下每条曝光及其排名
  （1 起），窗口仍是每会话最近 30 条；
- 当一次工具调用与某条曝光共享 ≥2 个实体键（或一个足够长的路径键），记一次使用命中，
  并把该条目的**最好排名**（同一 id 多次曝光取最小）计入分布；
- 因此 precision@k 的分母是**使用命中数**（`ranked`），不是召回次数、也不是曝光条数：
  它回答"在真正被用到的那些次里，有多少比例它排在 top-k"。

## 2. 健康面

- metrics：`retrieval.ranked`、`retrieval.precisionAt1`、`retrieval.precisionAt3`、
  `retrieval.precisionAt5`（`ranked > 0` 才出现）；
- 记忆行在"有效命中"后追加：
  `；命中排名：@1 a/b、@3 c/b、@5 d/b（used_tool 归因，分母是使用命中数）`；
- `ranked === 0` / 未接线：一个字都不写（不印 "@1 0/0"）；
- 文案由导出的 `retrievalRankNote()` 生成，单测钉住分母与空读数。

## 3. 明确边界

1. 这是**使用归因**统计，不是标注集上的 precision@k：没有被人用到的召回不进入分母；
2. 同一 id 多次曝光取最好排名，同一 id 多次使用各算一次（使用事件口径）；
3. 只统计本进程；`used` 仍然只用于 `effectiveRate`，两个口径分开报，不互相换算。
