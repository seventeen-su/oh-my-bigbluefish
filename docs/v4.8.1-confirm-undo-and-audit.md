# OMB v4.8.1 — 候选确认的撤销与审计

> 为什么是 x3 而不是 x2：撤销/审计/查询/批量都属于 **v4.8.0 候选确认功能**的收尾
> （同一命令、同一生命周期），不是独立功能，所以按 `x1.x2.x3` 走修复位 **4.8.1**。
> 独立于确认功能的"写入冲突提示"放在下一个功能版本（4.9.0）。

## 1. 问题

4.8.0 的 `/omb-confirm` 只能确认，不能撤销：

- 用户确认后改主意，没有任何入口；
- 撤销不能靠"看起来像候选"去猜——用户显式 `omb_remember` 的条目也是
  `assertedBy:user`，猜错会误伤用户原话；
- 确认本身没有审计记录，事后无法回答"谁在什么时候确认过"。

## 2. 存储 schema v5：确认审计

```sql
CREATE TABLE memory_confirm (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  memory_id  TEXT NOT NULL,
  action     TEXT NOT NULL CHECK (action IN ('confirm', 'undo')),
  session_id TEXT,
  at         INTEGER NOT NULL
) STRICT;
CREATE INDEX memory_confirm_memory ON memory_confirm(memory_id, at);
```

- v4 → v5 **纯加法**（只建新表），旧库原地升级；
- `SCHEMA_VERSION` 同步抬到 5，`migrate()` 的漂移自检继续生效；
- 读取面是结构能力 `asConfirmStore`（不进 ABI）：探测不到审计面时撤销 **fail-closed**；
- 只增不改：撤销不删 `confirm` 行，而是再写 `undo` 行；**当前状态 = 倒序第一条**。

## 3. `/omb-confirm` 的新形态

```text
/omb-confirm [list [offset] | log <记忆id> | <记忆id> | undo <记忆id>...]
```

| 子命令 | 行为 |
| --- | --- |
| 无参数 / `list [offset]` | 列出候选（每库最近 50 条里筛），分页；回执显示年龄，超过 30 天给 stale 建议 |
| `log <id>` | 列出该条的确认审计（confirm/undo、时间、会话）与当前状态 |
| `<id>` | 确认候选（只改 `assertedBy`，查回验证，写 confirm 审计） |
| `undo <id>...` | 批量撤销（≤10 条，逐条报告）；单条失败不影响其它条 |

撤销判据（全部满足）：条目当前是 `user` 且活跃；库有审计面；**审计最后一次动作是
`confirm`**。撤销只改 `assertedBy`（user→model），追加 `undo` 审计，写回后查回验证。

## 4. 状态面

- `confirm.commands / listed / logged / promoted / undone / refused`；
- 记忆行只在按过命令后追加：
  `候选确认：已确认 N 条[（撤销 M 条）]（命令 K 次，列出 L 次[，查询 Q 次][，拒绝 R 次]）`；
- 没按过命令、未接线：一个字都不写；
- 文案由导出的 `confirmHealthNote()` 生成，单测钉住"撤销/查询为 0 时不印"。

## 5. 明确边界

1. 没有自动晋升/自动撤销（确认与撤销都是用户命令）；
2. 撤销逐条或小批量（≤10），没有"全库撤销"；
3. 审计没有独立导出命令（`log` 只按 id 查）；
4. **本版不含写入冲突提示**（那是独立能力，见 4.9.0）。
