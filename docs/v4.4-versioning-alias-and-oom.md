# OMB v4.4 — 版本号实测计算 / 别名与调用图 / shell 推断写 / 冲突材料 / OOM 取证

> 本版两件事：① 版本号改为**从功能清单实际计算**（不再手写 4.1/4.2/4.3）；
> ② 收掉 v4.3 末尾的剩余项：导入图升级、shell 未知写推断、冲突材料包、OOM 取证。
> 当前计算版本：**4.5.0**（24 功能 / 79 小功能）；构建代见 `build-generation.json`。

## 1. 版本号：从功能数/小功能数计算

- 单一真源：`version-manifest.json`
  - `major`：架构代（当前 4，只有 ABI 不兼容才变）；
  - `features[]`：每个功能一个条目，`subfeatures[]` 是它的具体小功能；
  - 版本 = `major.功能数.累计小功能数`。
- 生成器：`scripts/version.mjs`
  - `node scripts/version.mjs --write`：写回根/7 个组件 `package.json` 与 `kernel/version.ts`；
  - `node scripts/version.mjs`（默认 `--check`）：校验是否漂移，门禁用。
- 代码单一来源：所有模块常量（artifact/memory/vector/notify/profile/reasoning）、
  `KERNEL_SELF`、注册测试都从 `kernel/version.ts` 的 `OMB_VERSION` 读取；不再手写版本字面量。
- 规则：新增/完成一个功能或小功能 → 改 manifest → 跑 `--write`；**禁止**手工改 package.json 版本。

## 2. 导入图升级（v4.3 的"完整导入图"落点）

- `extractImportDetails()`：说明符 + 命名导入本地名 + 其中"被当函数调用"的名字
  （`name(` 正则近似，明确不是类型系统）。
- `readAliasConfig()`：读 tsconfig/jsconfig 的 `baseUrl` 与 `paths`（`@/* → src/*`）；
  `resolveImportTarget()` 支持相对路径、别名、baseUrl 三种来源，只接受仓库内真实文件。
- 产出（画像 `structure`）：
  - `imports`：顶层目录边（v4.3，最多 12）；
  - `fileImports`：文件级导入边（v4.4，最多 12）；
  - `calls`：近似调用边（caller/callee/symbol/count，最多 12）；
  - `aliases`：识别到的 tsconfig 别名（最多 4 条）。
- `omb_project` L1 显示 `别名`、`文件依赖`、`调用` 的短摘要；总长仍 ≤2,400 字符。
- 边界：无语言服务、无类型解析、无包导出映射；解析不到就跳过，不猜。

## 3. shell 未知写推断（命令前后 git status 差分）

- 当 shell 命令提取不到明确写路径（`unknown`，如 `git apply`、构建脚本）且 `shellInferUnknown=true`：
  1. `tool/call` 时记录当前 `git status --porcelain=v2 -z` 脏路径基线；
  2. post-execute 成功后再取一次，**新增脏路径**记为 `shellInferred` 写；
  3. 这些路径进入 `shellWrites`/`recentWrites`，可触发"读后 shell 写 → deny"与状态行
     `shell 推断写 N`。
- 明确标注"推断"：并发写入可能被算进来；不是精确归属，不改自动合并行为。
- 有界：每会话 shell 写表 ≤32；基线每次覆盖，不累积。

## 4. 冲突材料包（不做自动合并）

- 读取文件时保存 base 正文（每会话最多 4 条、单文件 ≤64KB）。
- 守卫拒绝（内容变化 / shell 写 / 其他会话写且无法核验）时，写
  `<cwd>/.omb/conflicts/<timestamp>-<hash>.md`：
  - 文件路径、原因、时间；
  - base（读取时）与 current（现在）两段原文；
  - 明确写"事实材料，不是自动合并结果"。
- 拒绝理由含材料路径；最多保留 20 份，超出按 mtime 清理。
- 为什么不做自动三方合并：base 只在读取时可知，自动改写会绕过用户裁决；
  本版只提供可核验材料，合并交给用户/git。

## 5. OOM 取证与归属结论

**证据链（本会话/上轮实测）：**
1. 崩溃是 Node 4GB old-space 到顶（mark-compact 无法回收），不是某模块抛异常；
2. 两个被点名的表（`turnBySession`/`projectFailures`）条目小、只在事件上增长，
   无法解释 GB 级；已分别 256/32 有界；
3. **空闲 120 秒、无 OMB 事件、无工作区写入**时宿主仍从 1.44GB 涨到 1.63GB；
   之后同一进程 23 分钟到 2.9GB；
4. OMB 全仓库无周期定时任务（只有瞬时重试 timer）；6 模块 0 降级。

**结论**：这些证据排除"OMB 事件驱动表是主因"，但**没有 heap snapshot 不能最终定罪**；
宿主/第三方插件仍可能是 retained set 的来源。已提供 `scripts/heap-snapshot.ps1`
（`--heapsnapshot-near-heap-limit=1 --max-old-space-size=2048`），崩溃时生成快照，
用 DevTools 按 Retained Size 定位。`omb_status` 的 `## 进程` 段可先看趋势。
