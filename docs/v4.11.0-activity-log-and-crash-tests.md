# OMB v4.11.0 — 活动日志与崩溃窗口验证

> 用户指令第 5 项（x2 新功能）：补全**崩溃验证**与**日志系统**。

## 1. 活动日志（`modules/memory/activity.ts`）

之前 `omb_status` 只有累计计数，看不到"最近发生了什么"。本版加一个**有界、进程内、
只读展示**的活动面：

- 记录类别：`write` / `dedupe` / `promote` / `abstain` / `retrieve` / `confirm` / `error`；
- 环形最多 `ACTIVITY_LOG_MAX = 200` 条（超出按插入序淘汰）；detail 截断到 200 字符；
- **不落盘、不含记忆正文**：只记 id/动作/原因类别——审计仍在 `memory_confirm` /
  `memory_feedback` 表里，活动日志不是审计；
- 计数是累计的（淘汰不清零）；`errors` 单独计数，错误永不省略；
- 健康面：`renderActivityNote(summary)` 只列**发生过**的类别（不印 0 次），
  没有活动就一个字不写；metrics 暴露 `activity.total` / `activity.errors`。

接线：`omb_remember` 的写入/去重/升级/弃权/异常、`omb_recall` 的每次检索、`/omb-confirm`
的每次动作，都记一条（正文不进入日志）。

## 2. 崩溃窗口验证（`tests/dsh/project-evidence-crash.test.ts`）

子进程在**真实写入循环**中（`record()` 同步落盘）被父进程 SIGKILL，然后检查磁盘：

1. `evidence.json` 始终是可解析的完整 JSON（temp → rename 原子替换，不留半截文件）；
2. 重新打开账本能读到已提交条目（快照非空）；
3. 没有 `.corrupt-*` 现场（有的话说明文件被写坏过，而不是被杀在提交边界）。

实现细节：子进程用 Node 原生 TS 类型剥离直接加载 `dsh/project-evidence.ts`，
第一条 `tick` 后立即 `SIGKILL`；父进程解析/重新打开文件。CI 中真实执行，不模拟异常。

边界（写清楚，不假装覆盖）：本用例只覆盖**证据文件的原子写**；记忆库的崩溃恢复由
SQLite/WAL 自身保证，不在本用例观测范围内（没有做 SQLite 的 kill 测试）。
