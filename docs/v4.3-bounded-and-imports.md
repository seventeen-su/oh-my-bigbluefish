> ② 继续 v4.2 的"未完成"清单，落地**跨顶层目录的相对导入图**（不是完整调用图）。

## 1. 两个无界增长点：确认与结论

### 1.1 `turnBySession`（`modules/memory/index.ts`）

- **属实**：`turn/start` 时 `Map.set()`，原实现无删除、无上限。
- **修复**：`MAX_TRACKED_TURNS = 256` + `rememberTurn()`（先删后插近似 LRU，超出淘汰最旧）。
- **它是不是 OOM 元凶**：**不是主因**。每条只是 `sessionId → number`（约几十字节），
  即便十万会话也只有几 MB；而且只在 `turn/start` 事件上增长，**空闲时根本不写**。
  这与实测"进程空闲仍约 80–100 MB/分钟增长"矛盾。

### 1.2 `projectFailures`（`modules/memory/store.ts`）

- **属实**：失败记录只增不减（成功打开或淘汰已打开项目才会删），`status().detail`
  会把所有失败拼进一条文本。
- **修复**：`MAX_PROJECT_FAILURES = 32`；单条原因截断到 200 字符；状态面只展示前 5 条，
  其余只报总数。
- **它是不是 OOM 元凶**：**不是主因**。键是项目根、值是错误文本；要吃到 GB 需要
  数百万个不同失败路径。实测进程 19 分钟到 2.3 GB，而失败记录量级只有个位数/几十。

### 1.3 同时有界化的同类缓存（审查后主动排查）

| 位置 | 原状 | 现在 |
| --- | --- | --- |
| `modules/memory/artifacts.ts` | `cwd → git ls-files 索引` 无上限（每项可达上千路径） | `MAX_INDEX_CACHES = 16`，LRU |
| `dsh/reasoning-effort.ts` | `explicit`（每会话一条）无上限 | 128 条，LRU |
| `dsh/reasoning-effort.ts` | `capabilities`（每 provider/model 一条） | 64 条，LRU |

> 这些仍不是"已证明的 OOM 根因"；它们只是**本仓库内可见的有界化缺口**。
> 真实根因需要宿主侧 heap snapshot（见 §4）。

## 2. 进程内存读数（OOM 可观测）

`omb_status` 新增 `## 进程` 段：

```
## 进程
- Node v…：rss 512 MB / heapUsed 256 MB / heapTotal 300 MB / external 40 MB（uptime 1m）
```

- 数据来自 `process.memoryUsage()` / `process.uptime()`（`dsh/` 层，允许接触 process）；
- 渲染是纯函数 `renderProcessSection()`，非法读数写"未测量"，不写 NaN；
- 目的：崩溃前就能看到 rss/heap 趋势，而不是只剩崩溃栈。

## 4. 对 OOM 问题的判断（保留证据）

- 两个增长点**属实但不是元凶**；证据：
  1. 条目大小与增长触发条件都不支持 GB 级；
  2. 之前实测：**无 OMB 事件、无工作区写入的 120 秒内**，宿主仍从 1.44 GB 涨到 1.63 GB；
  3. 崩溃是 Node 4GB old-space 到顶（mark-compact 无法回收）。
- 因此 OMB 仍是"优先排查对象"而非"定罪对象"：没有 heap snapshot 前，不能断言
  泄漏在宿主、第三方插件还是 OMB 的某条路径。
- 下一步仍建议：`NODE_OPTIONS=--heapsnapshot-near-heap-limit=1`（可加
  `--max-old-space-size=2048` 让快照更早更小），崩溃后用 DevTools 看 retained size；
  现在 `omb_status` 的 `## 进程` 行可先用于观察趋势。
