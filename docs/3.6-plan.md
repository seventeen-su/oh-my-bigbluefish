### 1.1 现状（已核实的事实）

| 事实 | 位置 |

| 组件名/包/文案各有独立落点 | `kernel/display.ts:126-127`、`packages/privacy/**`、`locale/*.json`、`kernel/abi/catalog.ts` |

### 1.2 施工方案

**a) 目录与代码归属**

- `modules/privacy/**` → `modules/memory/privacy/**`（保持文件粒度，不做逻辑重写；`gate.ts` / `state.ts` / `commands.ts` / `durable.ts` / `modes.ts` / `codec.ts` 原样搬）。
- `modules/memory/index.ts` 的 `apply` 负责：注册 `SERVICES.privacy`（把现有 `createPrivacyModule` 的装配逻辑接进来）、注册 `/omb-privacy` 命令、把隐私读数并进 memory 的健康面与状态段。
- **服务名不变**（`SERVICES.privacy`）——artifact 侧一个字都不用改，这是"只改归属、不改契约"的关键。

**b) 行与包**

- `cordis.patch.yml` 删掉 `omb-privacy` 那一行（含其 config 块），**行序表与 `tests/dsh/module-graph-source.test.ts` 同步**。
- `kernel/display.ts` 删掉 `omb-privacy` 条目，其文案并入 `omb-memory` 的 description（"记忆库（含隐私闸门）"这类表述要由 `display.ts` 生成到 locale，**不手改 locale**）。
- 删 `packages/privacy/**`；`package.json` 的 `dependencies` 去掉 `@omb/privacy`；`pnpm-workspace.yaml` 无需改（glob 覆盖）。
- `kernel/abi/catalog.ts` 的 `derivedRequires`/`derivedCapabilities`：删除 privacy 模块条目，把它的能力并入 memory 条目（catalog 的纪律是"未知 id 抛"，所以**漏一处会当场失败**，正好当防线）。

**c) 依赖图**

- artifact 现在**间接依赖 memory**（因为 `SERVICES.privacy` 由 memory 提供）。行序上 memory 在前、artifact 在后 ✓ 已满足；但要在 artifact 的 `requires` 里**显式加上 `omb-memory`**，否则"缺服务"只能靠运行时降级发现——而 design 的硬纪律是"依赖缺席必须点名"。

**d) 命令与逃生口**

- `/omb-privacy` 命令名**保持不变**（用户肌肉记忆 + 文档已写）。命令注册从 memory 的 `apply` 走，`input.hint` 与 `PRIVACY_USAGE` 原样保留（含 3.5 刚加的 `forget` / `clear`）。

**e) 测试**

- `tests/modules/privacy/**` 全部改 import 路径到 `modules/memory/privacy/**`；`tests/dsh/*` 里凡是断言"9 行/8 行"、列出行名的用例同步改（`tests/dsh/modules.test.ts`、`assembly.smoke.test.ts`、`module-graph-source.test.ts`）。
- **反向断言（必须有）**：删掉 privacy 行之后，artifact 的制品写入仍受闸门约束（即"并入"没有把闸门弄丢）、`/omb-privacy` 仍可用。

### 1.3 判据

1. `pnpm verify` 绿，且 `tests/dsh/module-graph-source.test.ts` 在"行序 = 依赖图"上仍然通过（行少了一行但图仍闭合）。
2. `check-resolution` 报 **8 个 OMB 行**（原 9）全部可解析、可加载、有中文名。
3. 真机（换代后）：插件页少一行 `omb-privacy`，而记忆库那一行的描述里写明含隐私闸门；`/omb-privacy status` 与 `forget`/`clear` 照常。

### 1.4 风险

- **服务就绪时序变差**：privacy 原先在 memory **之前**装配，现在与 memory 同批。artifact 若在 memory 之前挂载并立刻写索引，`kernel.service(SERVICES.privacy)` 会短暂取不到——现有实现是**每次调用实时查服务**（3.5 的 precondition 修复），所以表现为"该次判定降级"，而不是崩溃；但要写一条测试钉住"memory 晚到时 artifact 不静默放行"。
- 日志/状态面里"omb-privacy"字样会成为历史名词：**不要留悬空引用**（文档、注释、错误文案都要改成"记忆库的隐私闸门"）。

### 2.2 billion-context 是什么，以及两条比它更重要的结构性发现（报告 A，来源已核）

**billion-context**：`github.com/ranxianglei/billion-context`——**不是插件，是本地 HTTP 代理**
（npm v0.1.185、560★、2026-08-06 建仓、单人高频迭代、2354 个 npm 版本）。

- 策略：**模型驱动**（注入 `compress`/`decompress`/`search_context`/`acp_status` 工具，由模型自己选区间与摘要）；**可逆**（块可单独恢复）；**增量折叠**（只压已消费增量，最近 ~50K 保原文）；触发为供需双闸门（供给 ≥0.45×窗口 且 增长 >50K）。
- **明确支持 dsh**：`dsh plugin --profile <name> add billion-context`。
- **许可证**：MIT **+ 一条署名附加条款**（用户可见产品须署名并链回仓库）→ GitHub 识别为 **NOASSERTION，不是纯 MIT**。我们只研究不 vendor，不影响本轮；**若你想直接采用它，这条需要你拍板**。
- 它自陈局限：单人、观察性、**无随机对照**、质量证据受 probe 饱和（85–95%）限制 → "宣称 ≠ 实证"的又一例。

**发现 1（决定性：比算法更重要）——真正障碍是挂载点。**

本机只有 web profile；顶层 `compaction-basic` 早已 `disabled: true`，**活实例在 `preset-omb` 的 `compaction` group 内部**
（无 config → `auto` 默认 true），补丁层**按 id 够不到它**——这正是 billion-context 的 issue **#1772** 描述的坑，且发生在**我们自己的环境**里。
当前阈值：窗口 1M × `thresholdRatio` 0.8 ≈ **80 万触发、保留约 16 万原文**（本机实际 `maxTokens` 未取到，故为近似值）。
**后果：如果 OMB 另加一套压缩而不处理它，就是静默双压**——两套策略互相拆台，且两边都以为自己在管上下文。

**发现 2（结构性）——DSH 恒定从最前面折叠 = 每次压缩都重写"折点之后的一切"。**

`selectCompactableRange` 的 `firstIdx` 恒为 surface 位置 0 或 1（`region.ts:131,151-154`）。
按 Anthropic 的缓存规则（层级 tools→system→messages，某层变化使其后全失效；**cache write 1.25×/2× vs read 0.1×，单价差 12.5×**），
折点紧跟 system ⇒ **每次压缩后 messages 缓存从位置 1 起全部失效**。
billion-context 宣称 cache-read 90.7–94.2%（4.5 个月实测），但**几何机制无法从公开材料复算**——报告已标"宣称 + 部分实测，须自测"。

**实证支持我们"确定性、无 LLM"的取向**：Complexity Trap（NeurIPS 2025，arXiv 2508.21433）在 SWE-bench Verified 五种模型配置上：
**observation masking 相对 raw agent 成本减半，解出率与 LLM 摘要持平甚至略高**；混合方案再降 7%/11%。这是目前唯一针对 coding agent 的公开对照实验。
另：KV 压缩（StreamingLLM / H2O / SnapKV）在推理引擎内部操作 KV 张量，**插件层够不到，属正交工作，不许声称能替代**。

**别人的失败模式（42 条已编号 issue）——这四条直接约束我们的设计**：

| issue | 现象 | 对我们的约束 |
| --- | --- | --- |
| #2193 | 1510 条 fold 锚点永久失配、连刷 166 条 no-anchor-match，**而面板仍报 netSaved 355.9M** | **自报指标会完全失真**：省下的 token 必须能被独立核对，不能只信自己的账 |
| #1995 | 滑窗每轮击穿 prompt cache | "每轮重写"这条路**已有人踩爆**——正是我们最怕的反例 |
| #1812 | 越压越大 | 压缩要有**净收益判据**，不是"跑了就算成功" |
| #1340 | 可逆性坏掉：把占位符当原文持久化了 | 落盘后**必须回读校验**（存进去的到底是不是原文） |

### 2.4 D2 的备选机制（本轮不实施）：运行时替换 summarize

**⚠ 2.4.0 一条把原计划推翻的实测（2026-10-06）**：仓库与 profile 的 `node_modules` 里**都没有**
`@deepseek-ai/dsh-compaction` / `-compaction-basic`，**连 `@deepseek-ai/cordis` 都没有**
（实测：`<repo>\node_modules\@deepseek-ai\*` 与 `<dsh-home>\profiles\web\node_modules\@deepseek-ai\` 皆不存在；
宿主其实是从 `<dsh-checkout>` 检出目录加载这些包的）。
→ 「`import { BasicCompactionEngine }` 然后继承」**编译期就过不去**（无论静态还是动态 import 都解析不到），
而把宿主包装进本仓库会直接违反既有的"`dsh/` 之外零宿主 import"边界与 `tests/dsh/no-host-imports.test.ts`。

**替代路线（不需要任何 import）**：**运行时取得实例、只替换它的一个方法**。

```ts
// dsh/compaction.ts（结构化面，零 import）
const engine = ctx.get?.('compaction')          // 宿主已注册的 compaction-basic 实例
const proto = Object.getPrototypeOf(engine)
if (typeof proto?.summarize !== 'function') → 如实降级（状态面写"未接上，原因：引擎形状不符"）
else engine.summarize = ourSummarize            // 实例属性遮蔽原型方法
```

为什么这条路成立（已按源码核实）：
1. `compaction-basic/src/index.ts:241-256` 的 `protected async summarize(...)` 是**唯一的子类定制点**（注释逐字："Override this sole hook for a template or remote summarizer"）；
2. `:437-441` 把它绑进 checkpoint 源时用的是**箭头闭包** `(input, owner, abort) => this.summarize(...)` —— 每次调用都重新读 `this.summarize`，
   所以**在实例上遮蔽**会在下一次压缩时生效；
3. `protected` 只是编译期约束，运行时它就是原型上的一个方法。

代价与纪律：
- **这是对宿主内部的运行时打补丁**，版本脆弱 → 必须先检查形状（原型上有没有 `summarize`），不符就**如实降级并写明原因**，绝不静默；
- **可回退**：保存原方法引用，disposer 里恢复（这也是"替代失败"时的运行时回退路径）；
- 只替换**摘要怎么写**，锁 / 区域选择 / surface 替换 / 工具配对 / 计价**全部继承宿主**——最容易写错的部分一行都不碰。

**其余形态**：

- 新增 `modules/compaction/`（**无宿主 import**，纯策略：checkpoint 生成、固化清单、报价、状态面文本、杀死判据）；
  `dsh/compaction.ts` 只做"取实例 + 换方法 + 形状检查 + 回退"。
- 新组件包 `packages/compaction/`（`@omb/compaction`）+ `kernel/display.ts` 条目 + `kernel/abi/catalog.ts` 条目 + `derivedRequires`/`derivedCapabilities`。
- **不再需要**给 peerDependencies 加宿主压缩包（因为零 import）——`tests/dsh/no-host-imports.test.ts` 的边界原样不动。
- `preset-omb`：**不再换掉 `compaction-basic` 那一行**（换成我们自己的实现无法解析依赖），改为在其后新增 `@omb/compaction` 一行，由它接管摘要实现；
  `tool-result-pruner` 与 `command-compact` 保留。
- 行数变化：隐私并入 −1、压缩新增 +1 → **仍是 9 行**。压缩组件有自己的控制面与状态段，满足 catalog「没有独立资源的开关不给独立行」的闸门。


### 2.5 早期的 summarize 方案（**已被 §2.7 取代，仅作 D2 备查**）

**a) 定制点（已核实）**：`BasicCompactionEngine` 在 `compaction-basic/src/index.ts:241-256` 把 `protected async summarize(input, agent, signal)`
标注为 "Override this sole hook for a template or remote summarizer"，并在 `:437-441` 把该钩子绑进 checkpoint 源。
→ 我们**继承全部机器**（锁 `assertNoActiveCompaction`、区域选择 `selectCompactableRange`、surface 替换、工具配对 `tool-pairing`、计价与 tokenMeter 记账），
只替换"摘要怎么写"。这是本设计里风险最低的一步：最容易写错的东西一行都不碰。

**b) 确定性 checkpoint（不调模型）**

- 走 `SummaryResult` 的**非 LLM 那一支**（`rawOutput?` + `llmStreamCall?: never`）——契约显式允许 "template, remote, or other summarizer"，
  所以这不是绕过接口，而是接口预留的一种实现。
- 价值不在于"省一次模型调用"，而在于**可核对**：摘要幻觉在这个方案里不可能发生，因为它不做摘要，只做**确定的取舍**。

- ⏳ **保什么／丢什么：待报告 A 定稿**。已确定的约束与候选：
  - **用户消息逐字保留**（OMB 的纪律是逐字，不做有损抽取）；
  - **工具轨迹结构化保留**（工具名 + 关键参数 + 成败 + 产物路径，一行一条；路径与命令逐字）；
  - **控制面快照**（复用我们已有的台账：当前档位、未闭合结论、最近验证、拉取过的视图、循环信号）；
  - **助手推理正文**：候选策略是"只保留最后一条 + 其余丢弃并在 checkpoint 里写明可从 seq 区间找回"；
    另一候选是"整段保留但把老工具结果 mask 掉"（observation masking 路线）。
    **选哪条要等 A 的对照证据**——这一条是 §2 唯一没有定稿的设计决策。

**c) 与记忆库组合（本组件的存在理由）**

1. **压缩前固化**：把被 shadow 区间里的持久事实先写进记忆库（走既有 `omb_remember` 的准入与**隐私闸门**，不绕过任何既有规则）；
   checkpoint 里只留**指针与取回指引**（"用 `omb_recall` 查 X"、"原文在 seq A–B、已被 shadow"）。
2. **库不可用时的降级**：跳过固化，在 checkpoint 里写明"**未固化**（记忆库不可用）"——不许假装固化过。
3. **报价**：shadow 之前先给出"要固化 K 条 / shadow N 个节点 / 约省 M token"（借 cognee 的 dry-run 思路；我们的 `ContextNodeCost.tokens` 已是价格一等公民）。

**d) 可见性（硬纪律：没有静默失效）**

- 状态面新增一段：本轮压缩 shadow 了哪些 seq、省了多少 token、固化了几条、**怎么取回**、有没有失败。
- checkpoint 文本本身要写明"这一段是怎么产生的、原文在哪、怎么取回"——让下一个模型知道**有什么被丢掉了**，而不是以为看到了全部。

**e) 判据（会失败的测试）**

1. 继承后的引擎在 `compactIfNeeded` 下仍满足宿主的锁与配对约束（用宿主的 `assertNoActiveCompaction` / 工具配对规则构造反例）。
2. `summarize()` 不调用 `ctx.llm`（用假 ctx 断言零调用）——"确定性"这件事要有**可失败的判据**，不能只写在文档里。
3. 记忆库不可用时：checkpoint 里出现"未固化"字样，且状态面同样报出（两种降级都要可见）。
4. 隐私：被 shadow 区间里的内容在 sealed 会话下**不进记忆库**（反向断言：不许因为"压缩"绕过闸门）。
5. 状态面数字与真实 shadow 集合一致（从宿主事件 `compaction/summary` 的 `shadowedSeqs` 反查）。

**f) 风险**

- **前缀缓存**：OMB 对"每轮变动的注入"极敏感。压缩本身是低频事件（阈值触发），但 checkpoint 一旦写入就成为新的前缀——**不许在里面放会变的东西**（时间戳、计数）。
- **可逆性**：shadow 之后原文是否还能取回，取决于宿主的重放机制；若不能，我们的"取回指引"必须落在**记忆库**这一侧（这就是 (c) 的存在理由）。
- **替代失败**：若我们的引擎在真机上导致上下文管理异常，回退路径是 `preset-omb` 换回 `compaction-basic`（一行），必须在文档里写明这一步。

## 3. 思维链质量强化 + 激励器评估（指令 3）

来源：研究报告 B（`_research/stress-and-gaming.md`，432 行，42 条出处 + 仓库 50 处行号，实证与主张分离）。

### 3.2 我们自己组件里的真缺口（**Lead 已按源码核实**）

**压力—严谨度方向反了。**

- `modules/reasoning/index.ts:609-617` 的**验证段**（"你还有 N 条结论未过形式核对"）写在 `else`（**非 tight**）分支里

- 净效果：**压力最大时，唯一必然出现的约束是循环提示**——而证据方向恰恰相反（压力升高 → 更倾向提前收尾、走捷径）。

### 3.3 裁决：**不新增"激励器"组件**

三条理由（都可核对）：

1. **通道重复**：注入文本 / 控制参数 / 状态面这三条通道 reasoning 已经全有（`index.ts:553-662`、`control.ts:54-82`、`index.ts:664-711`），新组件只能重复它们；
2. **预算**：常驻提示是全体组件共享的 **120 字符**（`kernel/abi/host.ts:86-93,122`），新组件必然抢预算；
3. **证据不足**："打气/施压"类干预最常被引用的正面证据（EmotionPrompt, 2307.11760）在独立复现里**未达显著**（2409.20303）。
   而真正有效的杠杆是**改收益结构**（判据与门槛），那属于 reasoning 的控制面，不是新组件。

→ 按 §5 的同一把尺子（catalog「没有独立资源的开关不给独立行」），**并入 reasoning 做**。

### 3.4 落地方案（三件，按优先级）

**A（最高优先，改动面小、可证伪）：压力—严谨度耦合**

- tight 档**恢复验证段**（把 609-617 移出 `else`，或改为"与档位无关"的独立注入）；
- **门槛只升不降**：`stopRule` / `evidenceLevel` 在 band=tight 时不得低于 standard（现在与 band 无关，等于"压力大时相对更松"）；
- 顺手修掉那句与代码相反的注释。
- **判据（用我们自己的台账做 A/B，可证伪）**：未闭合结论数、循环信号率、**"未经核对即断言"的比例**（`omb_verify` 报表里有）。
  预期方向：tight 下未闭合数下降、未经核对即断言的比例下降；若**反向**，这条改动就是错的，回退。

**B：显式"合法出口" + 判据重述（≤200 字符，由 stalled / no-new-evidence 触发）**

- 依据：**"诚实解仍可行"是压制生效的前提**，**"合法选项被封闭"会把 misalignment 从 0% 推到 96%**。
  所以当循环信号出现时，注入的不是"别绕圈"，而是**把出口写出来**：可以说"卡住了/需要更多信息/这条做不了"，以及**把完成判据重述一遍**。
- 硬约束：≤200 字符、**不写"不许作弊"**（那会提高评测意识）、**不写"你被监控"**。

**C：糊弄倾向——先只做状态面观察**

- 低召回高精度，**禁止写"检测到作弊"**（证据里 CoT 自述不可信：模型承认作弊 <2%）；
- 只报可核对的事实（例：连续 N 轮无新证据、同一结论反复断言而未 `omb_verify`、测试被改写/被跳过的工具调用痕迹），标注为"信号"而非"结论"。

### 3.5 明确不做的（反例清单，有据）

强调"别作弊/你被监控"→ 评测意识 + 混淆式作弊；把目标写成"让测试通过"→ 放大作弊；

### 8.7 ⚠ 接线前必须处理的一个实测陷阱：`isolate` realm（压缩流实测，2026-10-06）

压缩流用宿主的 vendored cordis 直接实探，得到三条结论（`vendor/cordis/src/reflect.ts:289-291` 有出处）：

1. 在**根 realm** 提供的 `toolResultPruner`，从 `isolate: { toolResultPruner: true }` 的**子 realm** 里 `get` 到的是 **`undefined`**；
2. 子 realm 可以有自己那一份，且**不覆盖**根 realm 的；
3. **同一 realm 里第二次 provide 同名服务会抛**（`service "x" has been registered at <fiber>`）。

而预设里那个 compaction 组**正是隔离的**（`cordis.patch.yml:192-194`：`isolate: { compaction: true, toolResultPruner: true }`），
`compaction-basic` 就住在里面。

**因此（修正 Lead 此前的判断）**：`dsh/host.ts` 的 `publishToHost` 已在真机跑通，指的是**根 realm 服务**（内核服务与就绪 promise），
**不能外推到隔离 realm**。我们的 provider 必须与 consumer（`compaction-basic`）**同 realm**——否则 pruner 注册"成功"了却谁也用不到，
又是一个"存在 ≠ 生效"。

**接线决定（看过预设结构后定死，2026-10-06）**：预设里那个组的形状是
`- id: compaction / name: cordis:group / isolate: {compaction: true, toolResultPruner: true} / config: [compaction-basic, command-compact, tool-result-pruner]`
（`cordis.patch.yml:188-204`）。因此：

1. **把 `@omb/compaction` 行加进这个组的 `config:` 列表内**（与 `compaction-basic` 同 realm）；
2. ⚠ **同时删掉组内 `tool-result-pruner` 那一行**——因为"同一 realm 内第二次 provide 同名服务会抛"，
   两行都在组内 = 直接抛错（不是覆盖，是加载失败）；
3. 组内 `tool-result-pruner` 原来的 `config`（`thresholdChars: 8192 / headChars: 4096 / tailChars: 1024`）
   **搬到 `@omb/compaction` 的 config 下**，语义不变（我们的默认值也照它）。

备选（只在选项 1 出问题时用）：
1. 把 `@omb/compaction` 行放进**同一个 `compaction` 组内**（与 `compaction-basic` 同 realm）；
2. 或去掉该组的 `isolate` 里 `toolResultPruner` 那一项（让服务回落到根 realm，与我们的发布点一致）——
   但这会改变宿主的隔离语义，需先确认 `compaction-basic` 仍能取到（它取的是同一路径）；
3. 或走**第二级回退**（在 consumer 所在 realm 的实例上遮蔽 `pruneSession`）——压缩流已实现该路径。

**判据（接线后必跑）**：状态面必须报出"实际走的哪一级 + 在哪个 realm"；
只报"已注册"而取不到实例 = 静默失效，视为未接线。

## 11. 上下文压缩：研究结论与"不做"的裁决（2026-10-06）

**用户裁决（原话要点）**：*"暂时不碰上下文压缩这一块，质量还不太好验证。"*
→ 本项目在此的**唯一交付是研究**（R1–R5 五份报告，见 §12/§13 与 `<worktrees>\_research\`），**没有留下任何实现**。

研究得到的、以后要用时可直接取的结论：

- **要优化的那一层是"压缩发生时"**（引擎何时折、折哪段、摘要怎么写），**不是"平时"裁短工具结果**——后者是宿主 `tool-result-pruner` 本来就有的行为（默认 8192 字符 / head 4096 / 尾 1024，只在引擎跑修剪那趟触发），动它属于方向错层；
- **挂载点不是障碍**：那个 `compaction` 组就定义在我们自己的 `cordis.patch.yml` 里，我们**能换行**（宿主 package 的 `--patch` overlay 做不到，billion-context 的 #1772 至今未修）；
- **依赖是障碍**：`@deepseek-ai/*` 在运行期解析路径上不存在（`MODULE_NOT_FOUND`），且我们自己的护栏禁止 `dsh/` import 宿主包 → **不能继承宿主引擎类**，只能自己重写；
- **但有一条零 import 的路**：`summarize()` 全包唯一调用点写成 `this.summarize(...)`（动态派发）→ **原型接管**即可替换摘要；
- **判据已有且验过分辨力**：见 R3；**"不许听自己报数"**这条有 billion-context 自己的 issue #2200/#2202 作为反面实证；
- **未决的真问题**：折叠点（恒定从最前面折）带来的前缀缓存失效（实测压缩后首次请求命中 6.01%、约 17.2 万 token 按全价重算）——那不在摘要这条路上，动它等于整换引擎（14 条不变式自写），风险高一个量级。
