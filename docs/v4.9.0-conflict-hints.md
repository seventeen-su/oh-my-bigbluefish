# OMB v4.9.0 — 写入冲突提示

> 这是**独立功能**（与 4.8.0 的候选确认、4.8.1 的撤销审计不同）：写新结论时，
> 回执里给出库里共享实体键的既有条目，让"可能矛盾"在写入当下可见，
> 而不是等召回合把两条结论一起端上来。按 `x1.x2.x3` 纪律：新增能力 → **4.9.0**。

## 1. 问题

4.7.0 的控制器只在用户说"不对/改成"时触发 `lookup` 并给旧 id；用户直接陈述新结论
（"现在用 Postgres 了"）时，旧结论仍活跃，两条会在召回里并存：

- 模型无法在写入当下知道"这条可能是在推翻什么"；
- 用户确认候选时也看不到库里已有的相关条目；
- 去重只处理**完全相同**内容，近义/相反内容不会互相提示。

## 2. 做法：只读的"可能相关"提示

`modules/memory/link.ts` 新增 `findRelatedRecords(store, record, options)`：

- 同作用域、**活跃**（未失效/未被取代）、内容不同；
- 与新条目共享 **≥2 个实体键**（路径/命令/包名/项目名；单键重合不算）；
- 每库候选上限 20，最多返回 3 条；
- 失败返回空数组（提示不能影响写入本身）。

判据与自动连边（4.7 起）同源，但**只读**：不建边、不改库、不决定是否冲突。

## 3. 出现在哪里

| 场景 | 位置 | 措辞 |
| --- | --- | --- |
| `omb_remember` 成功回执 | 回执末尾 | `可能的既有结论（共享实体键；只提示，未改库）：…若本条是对其中某条的更正，请用 supersedes=["id"] 重写；若两条都成立，忽略本提示。` |
| `/omb-confirm <id>` 成功回执 | 回执末尾 | 同上，另加"若与其中某条矛盾，先用 /omb-feedback 或 omb_remember(supersedes) 处理旧条目" |

实现上通过 `MemoryWriteDeps.findRelated` 端口注入（模块不直接依赖 `link.ts`，
避免 remember → link → capture → remember 的循环），`modules/memory/index.ts` 装配。

### 3.1 语义通道（v4.9.1，x3 收尾）

词法通道只能看见"共享实体键"的条目；没有路径/命令/标识符的纯自然语言结论
（"这个项目以后用 Postgres"）不会命中。v4.9.1 补上**向量通道**：

- `findSemanticRelated(store, record, embedder)`：嵌入新条目正文 → `searchVector`
  （归属 model/dim/revision 由库校验，跨空间向量不召回）→ 同作用域、活跃、内容不同、排除自身；
- 装配层（`index.ts` 的 `relatedFor`）**先词法后语义**、按 id 去重、最多 3 条；
  有嵌入器才跑语义通道，`omb-memory-vector` 关闭/无向量/维度不符/检索抛错时静默退回词法；
- 回执标注判据来源：词法条目带共享键（`词法`）、语义条目标注 `语义`，
  标题写作"共享实体键 / 语义相近"——**通道可解释，不混说**。

## 4. 明确边界

1. **不自动 supersedes、不自动拒绝写入**：共享实体键或向量相似只能证明"相关"，
   不能证明"矛盾"；
2. **语义通道是可选的**：没有嵌入器/尚未编码向量时只剩词法；语义相似不等于矛盾，
   近义改写也可能只是同一主题的另一面；
3. 只影响回执，**不改变任何库状态**（无边、无 validTo、无 supersededBy 写入）。
