# OMB v4.13.0 — 事件驱动记忆控制器：显式状态机

> 用户指令第 7 项（x2）：把控制器从"事件 reducer + 执行"整理成**显式状态机**，
> 补上转移审计、动作幂等与失败分类，并接入活动日志。

## 1. 显式阶段与转移

`ControllerSessionState` 新增：

- `phase`：`idle` / `candidate-pending` / `tracking-tasks` / `mixed`
  ——由**表内容推导**（候选/任务），不另存影子变量；
- `transition`：最近一次 `{ event, from, to, actions, at }`，
  状态面能看到"什么事件把状态推到了哪里"。

`reduceMemoryEvent` 是唯一入口：所有 reduce 路径（用户消息/工具结果/回合结束/
已写入）都经过同一层包装计算 phase 与 transition，避免"某条分支忘了更新状态"。

## 2. 动作 id 与幂等

- 每个动作带确定性 `id`：
  `persist=candidate.id`、`lookup=lk_<fingerprint>`、`request-model=rm_<fingerprint>`、
  `track-task=tt_<fingerprint>`、`expire-task=ex_<fingerprint>`；
- 执行侧对 `persist` 做**幂等**：每会话记录最近 64 个已成功候选 id，
  重复投递直接跳过并计 `duplicateActions`（写路径的去重仍兜底）；
- lookup/request-model **不**做全局幂等：同一提示在不同时点可能需要再次出现
  （它改变的是模型注意力，不是库状态）。

## 3. 失败分类

`ControllerStats.failures` 按 8 类计数：`privacy` / `dedupe` / `cap` /
`disabled` / `store-missing` / `verify-failed` / `lookup-failed` / `unknown`。
分类由写路径/执行路径的**可读原因**确定性映射（`classifyControllerFailure`），
不把"去重/隐私/库未就绪/查回失败"混成一个数；健康面只在有失败时列
`失败分类：…`，metrics 按类输出 `capture.controller.failures.<kind>`。

## 4. 活动日志接入

控制器动作与失败进 v4.11.0 的活动日志（`controller` / `error` 两类，
只记动作类型与原因，不含正文）；健康面活动读数因此能回答"控制器最近做了什么"。

## 5. 边界

- 控制器仍是**纯 reducer**：零 I/O、零时钟、零 LLM；
- `phase` 只在事件到达时更新；没有事件就不会"自己变"；
- 失败分类依赖原因字符串（写路径的中文原因），是**可解释的近似**，
  不是异常类型系统；未知原因归 `unknown`，不静默丢掉；
- 幂等只覆盖 persist：lookup/request-model 的重复是刻意的。
